## 一、性能：回答为什么慢

### P0-1｜`search_knowledge_graph` 把「标的物」当企业名查，kg 类问题必然检索错位

**位置** `src/rag_agent/tools/rag_tools.py:259-298`（`_query` 方法）

**现象** kg-001「有哪些关于空调的采购?」忠实度只有 2，报告写"来源仅企业名单，回答却列出奥克斯等来源外实体"。

**根因** `_query` 的五个分支全部按**企业名称字段**做 `LIKE` 匹配：

```python
# profile:   enterprise_企业信息 WHERE company_name LIKE %s
# wins:      bid_subjects WHERE winner    LIKE %s
# purchases: bid_subjects WHERE purchaser LIKE %s
# agency:    bid_subjects WHERE agency    LIKE %s
# violations:enterprise_违法违规记录 WHERE company_name LIKE %s
```

**没有任何一个分支按「标的物」或「类别」查询**。于是「空调」被送进 `company_name LIKE '%空调%'`，命中的是名字里带"空调"的**公司**（如 XX 空调设备有限公司），而不是空调这类采购标的。模型拿到一堆无关企业名，只能凭记忆补出"奥克斯"。

**改法** 给 `GraphRelation` 增加标的物维度，新增两个分支：

```python
GraphRelation = Literal["all", "profile", "wins", "purchases", "agency", "violations", "subject", "category"]

# subject: 按标的物名查采购/中标记录
elif rel == "subject":
    sql = ("SELECT title, category, purchaser, agency, winner, award_amount, award_time, province, city"
           "  FROM bid_subjects WHERE subject LIKE %s ORDER BY award_time DESC LIMIT {n}")
# category: 按类别（工程/货物/服务）聚合
elif rel == "category":
    sql = ("SELECT category, COUNT(*) AS cnt FROM bid_subjects"
           "  WHERE category = %s GROUP BY category LIMIT {n}")
```

同时把工具描述里"实体名称"改成"企业名称**或标的物名称**"，让模型知道这里能按标的物查。

**前置条件（实际核查后修正）**：MySQL 的 `bid_subjects` 只有 18 列，**没有 `subject` 列**；标的物列只存在于 PostgreSQL 的 `bid_subjects`（由 `to_postgresql.py:96` 的 `("标的物", "subject", "VARCHAR(512)")` 建出）。

所以标的物检索不能加在 MySQL 的 `search_knowledge_graph` 上（会 `Unknown column 'subject'`），正确位置是 PG 工具——给 `PostgresqlArgs` 增加独立参数：

```python
subject: str | None = Field(default=None, description="标的物名称或关键词，如'空调'")
# run() 里：where.append("subject LIKE %s"); params.append(_like(args.subject))
```

**收益** kg-001/kg-003 从"把标的物当企业名查、必然错位"变成可正确检索。但**前提是 PostgreSQL 已装并导入数据**——MySQL 侧没有标的物数据，装库前这两类问题仍无法回答，只能如实说明。

### P0-2｜两个工具的描述重叠，导致 pg-001 路由错位

**位置** `rag_tools.py:214-218`（`SearchKnowledgeGraphTool.description`）与 `323-326`（`SearchPostgresqlTool.description`）

**现象** pg-001「重庆稳信科技有限公司中标了哪些项目?」期望走 `search_postgresql`，实际走了 `search_knowledge_graph`。

**根因** 两份描述都在声称自己能答同一类问题：

```
search_knowledge_graph: "...适用于企业画像、'某公司中标了什么/被处罚了吗'等实体关系类问题"
search_postgresql:      "...适用于：找招标/中标项目、查某企业中标了什么、按地域/类别/时间/金额筛选"
```

`某公司中标了什么` 这句话**两边都有**。工具模型（`glm-4.5-air`）没有额外信息来判断该选哪个，只能随机偏向先注册/描述更长的那个。

**改法** 划清边界，各自**只说自己的独有能力**，并显式写"不要用于"：

```python
# search_postgresql
"检索 PostgreSQL 招标采购标的物记录（含中标结果）。用于：按中标人/采购人名称查项目清单、
按地域/类别/时间/金额筛选、排序聚合。需要项目明细（名称、金额、时间）时用本工具。"

# search_knowledge_graph
"查询企业维度的关联档案：工商信息（法人/注册资本/信用等级）、违法违规记录、
以及该企业作为采购人/代理机构的项目。只返回关系概览，不返回完整项目明细——
需要项目明细请改用 search_postgresql。"
```

**收益** 消除歧义。工具描述是 function calling 里**唯一的**路由依据，比在提示词里写规则有效得多。

### P1-3｜rerank 每次检索多花 1.8 秒，是单项最大延迟

**位置** `src/rag_agent/retrieval/rerank.py:59-74`（`_rerank_llm`）

**现象** 代码注释自述"glm-4.5-air 打分一次 ~1.8s"。一次问答里每个检索工具都会触发一次，3 个工具就是 5.4 秒纯等待。

**根因** 用 LLM 做 listwise 打分，把一个本该几十毫秒的排序操作变成了又一次大模型调用。

**改法** 三条路，按投入排序：

1. **最快见效**：`.env` 设 `RERANK_BACKEND=off`，立刻省掉全部 rerank 时间，代价是排序退化为融合序。
2. **折中**：只对**候选数 > 8** 的情况 rerank，候选少时融合序已经够准（当前 `CANDIDATE_CAP=16`，可以改成 `if len(texts) < 8: return None`）。
3. **根治**：接专用 rerank 接口（`RERANK_BACKEND=api` 已经写好，见 `rerank.py:97-122`），比如 SiliconFlow 的 `bge-reranker-v2-m3`，延迟约 50ms，比 LLM 快 30 倍且判别度更高。

**收益** 方案 1 立刻省 1.8s×N；方案 3 在保留排序质量的前提下把 rerank 从瓶颈变成噪声。

### P1-4｜embedding 每次都重新算，同一 query 重复付网络往返

**位置** `src/rag_agent/retrieval/vector_store.py:39-44`

```python
def search(self, query: str, top_k: int = 5) -> list[dict]:
    q = np.asarray(embed_texts([query])[0], dtype="float32")  # 每次都是真实 API 调用
```

**根因** `embed_texts` 走智谱 `embedding-3` 接口，没有缓存。而 `_hybrid_hits`（`rag_tools.py:70-80`）在一次工具调用里会分别查 legal/policy/faq 三个库，**同一个 query 被 embed 三次**。

**改法** 在 `embed_texts` 外层加按文本的缓存：

```python
from functools import lru_cache

@lru_cache(maxsize=256)
def _embed_one(text: str) -> tuple[float, ...]:
    return tuple(embed_texts([text])[0])
```

**注意** `lru_cache` 对 `list` 不可哈希，所以要用返回 tuple 的包装函数，不能直接装饰 `embed_texts`。

**收益** 单次问答省 2 次 API 往返（约 0.6~1.5s），重复提问场景收益更大。

### P1-5｜`neo4j_client` 每次查询都新建并关闭 driver，连接池形同虚设

**位置** `src/rag_agent/retrieval/neo4j_client.py:26-49`

```python
def query(cypher: str, **params) -> list[dict]:
    driver = _driver()          # 每次新建
    try:
        with driver.session() as session:
            ...
    finally:
        driver.close()          # 每次关闭
```

**根因** Neo4j 的 `Driver` 内部就是连接池，**应该全局复用**。现在每次 `query()` 都经历"建池 → 建连接 → 销毁池 → 拆连接"的完整开销，单次约 30~100ms（含 TLS 握手，Aura 上更贵）。

`graph_tools` 里 `_entity_profile` 可能在一次工具调用中多次 `query()`，开销会叠加。

**改法** 改成模块级单例：

```python
_driver_singleton = None

def _driver():
    global _driver_singleton
    if _driver_singleton is None:
        from neo4j import GraphDatabase
        s = get_settings()
        if not s.neo4j_uri:
            raise Neo4jNotConfigured(...)
        _driver_singleton = GraphDatabase.driver(s.neo4j_uri, auth=(s.neo4j_user, s.neo4j_password))
    return _driver_singleton

def query(cypher, **params):
    with _driver().session() as session:   # 不再 close
        return [{k: r[k] for k in r.keys()} for r in session.run(cypher, **params)]
```

进程退出时 driver 会被 GC 回收，不需要显式 `close()`。

### P2-6｜注入脚本逐行 MERGE，8789 行 = 8789 次网络往返

**位置** `scripts/import_to_neo4j.py:150-190`

**根因** 每行单独 `query(cypher, **params)`，每行一个事务一次往返。

**改法** 用 `UNWIND` 批量，每批 500~1000 行：

```python
BATCH = 500
for i in range(0, len(rows), BATCH):
    chunk = [prepare(r) for r in rows[i:i+BATCH]]   # 先清洗成 dict 列表
    query("""
        UNWIND $rows AS r
        MERGE (i:Item {name: r.item})
        FOREACH (_ IN CASE WHEN r.pur IS NULL THEN [] ELSE [1] END |
            MERGE (p:Purchaser {name: r.pur})
            MERGE (p)-[:采购 {amount: r.amount}]->(i))
        ...
    """, rows=chunk)
```

**收益** 8789 次往返 → 18 次，注入时间从分钟级降到秒级。

### P2-7｜`get_data_coverage()` 被 `lru_cache` 永久冻结

**位置** `src/rag_agent/agent/prompt.py:10-11`

```python
@lru_cache(maxsize=1)
def get_data_coverage() -> dict[str, str]:
```

**根因** 整个进程生命周期只查一次 PG。你后续往 `bid_subjects` 增量导入数据后，提示词里的"数据覆盖范围"**永远停在上次启动时的值**，模型会按过时的范围换算"近半年"。

**改法** 换成带 TTL 的缓存（或干脆每次查，反正是一条 `MIN/MAX` 聚合，走索引是毫秒级）：

```python
import time
_cache: tuple[float, dict] | None = None
_TTL = 300.0

def get_data_coverage() -> dict[str, str]:
    global _cache
    if _cache and time.time() - _cache[0] < _TTL:
        return _cache[1]
    ...# 查库
    _cache = (time.time(), result)
    return result
```

## 二、检索质量：评估暴露的问题

### P0-8｜评估脚本的关键词匹配没做归一化，指标天然误报

**位置** `evals/run_eval.py:96-99`

```python
haystack = out["answer"] + "\n" + "\n".join(s["title"] for s in out["sources"])
found = [k for k in out["keywords"] if k and k in haystack]
```

**现象** kb-001 评审 5/5/5 满分，但 `keyword_pass=False`，因为回答写"7 个工作日"（中间有空格），关键词是"7个工作日"。

**根因** 裸子串匹配。中文里空格、全半角、标点差异都会导致误判。同类隐患还有 kb-002 的 `"2%"`（回答可能写"百分之二"）。

**改法** 匹配前对两边做归一化：

```python
import re, unicodedata

def _normalize(s: str) -> str:
    s = unicodedata.normalize("NFKC", s)      # 全角→半角
    return re.sub(r"\s+", "", s)              # 去掉所有空白

h = _normalize(haystack)
found = [k for k in out["keywords"] if k and _normalize(k) in h]
```

**但要注意**：归一化只能解决"空格/全半角"，解决不了"2%" vs "百分之二"这种**语义等价**。所以你说得对——关键词指标只能当粗筛。建议在报告里把它降级为"辅助指标"，**主判据用 LLM 评审的三个维度**。

### P0-9｜图谱类用例的 `expect_tools` 与工具实际能力不匹配

**位置** `evals/dataset.jsonl:7-9`（kg-001/002/003）

```json
{"id": "kg-001", "question": "有哪些关于空调的采购?", "expect_tools": ["search_knowledge_graph"]}
{"id": "kg-002", "question": "采购最多的标的是什么?", "expect_tools": ["search_knowledge_graph"]}
{"id": "kg-003", "question": "空调的供应商和采购人有哪些?", "expect_tools": ["search_knowledge_graph"]}
```

**根因** 三个问题问的都是**标的物维度**（空调、采购最多的标的物），但 `search_knowledge_graph` 只支持**企业维度**查询（见 P0-1）。用例设计时假设了工具具备它并不具备的能力。

**改法** 两件事拆开处理：

1. **修工具**（P0-1）：给 `search_postgresql` 加 `subject` 参数。注意位置在 PG 工具而非 MySQL 图谱工具（MySQL 表无该列）。
2. **用例保持不动**：`expect_tools` 无需改。问题不在用例写错，而是**工具没实现它声称要支持的能力**——这正是"指标本身是对的，暴露的是真实缺陷"的典型例子。

**否则这个指标永远是假的**：工具命中不代表答对，答错也不代表工具没命中。

### P1-10｜网址类问题缺少"只能原样复制"的硬约束

**位置** `src/rag_agent/agent/prompt.py:56-60`（联网搜索的工作方式）

**现象** web-002 问"全国公共资源交易平台官方网址"，回答给了 `www.ggzy.gov.cn`，参考是 `deal.ggzy.gov.cn`，正确性 2 分。

**根因** 提示词只写了"URL 必须原样给出，禁止省略"，约束的是**格式**（不许缩写成"官网"），没约束**来源**。模型看到"全国公共资源交易平台"这个它熟悉的概念，就从记忆里补了个域名，而不是从 Tavily 返回结果里复制。

**改法** 在提示词里加一条来源约束：

```
5. 涉及网址、电话、文号、具体数字时，只能从检索结果中原样复制，
   禁止凭印象补全或"纠正"。若检索结果中找不到，就说明"未检索到官方网址"，
   不要给出你记忆中可能正确的答案。
```

这条和 P0 里 pg-003 的幻觉修复是同一类问题（**记忆补全**），可以合并成提示词的一个小节「禁止来源外补全」，一次覆盖网址、金额、项目名三类。

### P1-11｜历史压缩在请求链路上同步执行，首字延迟被拉长

**位置** `src/rag_agent/agent/memory.py:93-96` + `api/chat.py:48-55`

```python
if len(stale) >= COMPRESS_MIN_BATCH:
    summary = _compress(prev_summary, stale)      # 同步 LLM 调用，~1.5s
    save_session_memory(...)
```

**根因** 压缩发生在**每次提问的请求路径上**，而且是同步阻塞。`chat.py` 虽然把 `history_secs` 计入总用时，但用户感受到的是"点了发送后先卡 1.5 秒才开始"。

**改法** 两条：

1. **改异步**：把 `_compress` 扔到后台线程，本次请求先用旧摘要 + 逐字拼接顶上，下次请求就能用上新摘要。
2. **改触发点**：不要等"攒够 3 组"，而是在**上一次回答结束后**（`finish_qa_record` 之后）就触发压缩，把成本挪到用户不等待的时段。

**收益** 长会话场景下每次提问省 1.5s 左右。

### P2-12｜ReAct 循环是全串行的，首 token 延迟叠加

**位置** `src/rag_agent/agent/agent.py:120-175`

**根因** 每一轮都要等 LLM 完成"分析 + 决定调哪些工具"（非流式，`glm-4.5-air` 约 0.7~1.2s），然后串行执行工具，再进下一轮。3 轮下来光工具轮就 3~5 秒，而且这期间**一个字都不输出**。

**改法** 两个层次，按改动量排：

1. **低改造成本**：模型一轮返回多个 `tool_calls` 时，**并行执行**（现在是 `for tc in msg.tool_calls` 串行）。用 `ThreadPoolExecutor` 包一层，3 个工具并行后从 ~6s 降到 ~2s。
2. **中等改造成本**：分析阶段就开始流式输出（把 `stage=analysis` 的 thought 实时 `yield` 给前端），让用户先看到"正在分析…"，体感延迟大幅下降。前端已经有 `stage: analysis` 的事件处理，只是后端没流式发。

### P2-13｜`SparseIndex.search` 全量扫描，语料涨了就线性变慢

**位置** `src/rag_agent/retrieval/sparse.py:62-81`

```python
for tok in set(q_tokens):
    for i, doc in enumerate(self.doc_tokens):   # 每个 token 扫全量文档
        tf = doc.count(tok)
```

**根因** 没有倒排索引，每个 query token 都要遍历全部文档。当前 1 万条语料下是 `tokens × 10000` 次 `list.count`，实测还能接受；但语料涨到 10 万就是十倍慢。

**改法** 建索引时顺便构建 `tok -> {doc_idx: tf}` 的倒排表：

```python
self.inverted: dict[str, dict[int, int]] = {}
for i, doc in enumerate(self.doc_tokens):
    for tok, tf in Counter(doc).items():
        self.inverted.setdefault(tok, {})[i] = tf

# search 里
for tok in set(q_tokens):
    postings = self.inverted.get(tok)
    if not postings: continue
    idf = ...
    for i, tf in postings.items():     # 只遍历命中文档
        ...
```

**收益** 检索耗时从 O(语料量) 降到 O(命中文档数)，语料扩容时不会成为瓶颈。内存代价约几十 MB（1 万条语料下）。
