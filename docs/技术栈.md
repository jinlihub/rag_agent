### 1.2 一句话概括选型取向

这个项目的技术选择有两条主线：

1. **能用标准协议解决，就不引入框架**。模型走 OpenAI 兼容协议、检索走 numpy 手写、索引走文件、事件流走标准流式响应——没引入 LangChain、LlamaIndex、向量数据库、消息队列。
2. **每个外部依赖都留了降级路径**。项目库没装时工具返回可读错误而非崩溃；图库没配时图查询工具自行退出；重排不可用时保持融合序。系统可以"部分能力缺失但不整体瘫痪"地运行。

## 2. 运行时与语言

### 2.1 Python 3.13.18

| 项 | 说明 |
| --- | --- |
| 作用 | 后端服务、数据加工脚本、评估运行器 |
| 版本约束 | `requires-python = ">=3.13"`（见 `pyproject.toml`） |
| 实际版本 | 3.13.18，位于项目内 `.venv` |

**选型理由**：

- 项目重度使用 `str | None`、`list[dict[str, Any]]` 这类新式类型标注，3.13 下无需 `from __future__ import annotations` 也能正常工作（代码里仍保留该导入以兼容）。
- 数据加工脚本大量使用 `Path`、`dataclass`、`match` 等现代特性，无需引入第三方工具库。
- 包管理用 uv，Python 版本由 `.python-version` 与 `requires-python` 双重约束，环境可复现。

**注意**：项目不是从源码编译 Python，直接用 uv 管理的独立解释器，与系统 Python 隔离。

| 作用 | 前端依赖安装、Vite 开发服务器与打包 |

## 3. 前端技术

### 3.1 Vue 3.5.44（Composition API）

| 项 | 说明 |
| --- | --- |
| 作用 | 页面与组件框架 |
| 版本 | 3.5.44 |
| 关键用法 | 全项目使用 `<script setup>` + Composition API |

**选型理由**：

- 问答页的状态复杂度集中在"流式消息追加 + 多阶段状态 + 滚动跟随"，`ref` / `computed` / `watch` 能把这类逻辑拆成独立的响应式单元，比选项式 API 更清晰。
- 组件内需要大量组合逻辑（流式解析、耗时聚合、关键词搜索），Composition API 的函数复用比 mixin 更可控。
- 单文件组件把模板、逻辑、样式放在一处，对"问答页、后台列表页"这种页面级重逻辑的文件更易维护。

**实际用法特征**：`ChatView.vue` 单文件承载了流式接收、来源渲染、耗时行、模型选择、历史抽屉、对话内搜索等多块逻辑，是本项目最复杂的文件——这正是选择 Composition API 的直接原因。

### 3.2 Vue Router 4.6.4（History 模式）

| 项 | 说明 |
| --- | --- |
| 作用 | 页面路由、登录守卫、管理员守卫 |
| 版本 | 4.6.4 |

**路由表**（`frontend/src/router/index.ts`）：

| 路径 | 页面 | 守卫 |
| --- | --- | --- |
| `/login` | 登录页 | `public`，已登录时重定向到 `/chat` |
| `/chat` | 问答页 | 需登录 |
| `/admin/qa-list` | 维护后台 | 需登录 + `requiresAdmin` |
| `/` | 重定向到 `/chat` | — |
| `*` | 重定向到 `/chat` | — |

**选型理由**：History 模式让 `/admin/qa-list` 这类路径可读、可分享；守卫逻辑集中在一处，避免每个页面重复判断登录态。前端守卫与后端 `require_admin` 双重校验——前端守卫只为体验，权限以后端为准。

### 3.3 Pinia 3.0.4

| 项 | 说明 |
| --- | --- |
| 作用 | 全局登录态（令牌、用户信息、是否管理员） |
| 版本 | 3.0.4 |
| 现状 | 仅一个 `auth` store；问答消息、后台筛选等状态留在组件内 |

**选型理由**：登录态是跨页面共享的唯一强需求（路由守卫、请求头注入都要用）。其余状态生命周期都在单页面内，放进 store 反而增加耦合，所以刻意**没有**把消息列表、筛选条件上提。这是克制的用法，不是能力不足。

### 3.4 Element Plus 2.14.7 + 图标 2.3.2

| 项 | 说明 |
| --- | --- |
| 作用 | 后台表格、筛选表单、日期选择、分页、弹窗；C 端基础输入与提示 |
| 版本 | 2.14.7 / 2.3.2 |
| 引入方式 | `unplugin-vue-components` 按需自动注册，无需手动 import |

**选型理由**：

- 维护后台的形态是"筛选区 + 表格 + 行操作 + 分页"，这类企业级组件是 Element Plus 最成熟的部分，表格固定列、长文本溢出提示都有现成能力。
- 问答页的对话气泡、回答卡片、来源面板是定制 UI，**没有**用组件库硬套，只复用按钮、输入框、下拉、弹窗等基础件。

**实际用法特征**：`element-plus` 在 `vite.config.ts` 的 `manualChunks` 里被单独拆包，避免与业务代码混在一个 chunk 里。

### 3.5 Axios 1.21.0

| 项 | 说明 |
| --- | --- |
| 作用 | 常规接口请求（登录、历史、后台、模型清单、埋点、图片解析） |
| 版本 | 1.21.0 |
| 封装位置 | `frontend/src/api/http.ts` |

**选型理由**：拦截器是刚需——统一注入 `Authorization` 头、统一把 401 打成"需要重新登录"、统一错误文案提取。Axios 的拦截器模型比 `fetch` 手写包装更直接。

**注意**：问答接口不走 Axios——它返回的是流式事件，需要用原生 `fetch` + 流读取逐帧解析，见 §3.7。

### 3.6 marked 15.0.12 + DOMPurify 3.4.17

| 项 | 说明 |
| --- | --- |
| 作用 | 把模型返回的 Markdown 渲染为 HTML，并消毒后再插入页面 |
| 版本 | 15.0.12 / 3.4.17 |

**选型理由**：

- 模型输出天然带 Markdown（列表、加粗、表格），不渲染会丢失结构。
- **回答内容是外部模型生成的，直接 `v-html` 等于把 XSS 风险交给模型**。所以渲染链路固定为：`marked 解析 → DOMPurify 消毒 → 插入`，白名单过滤脚本、事件属性、危险链接。这不是可选项，是这条链路的必要组成。

### 3.7 流式响应的消费方式（无第三方库）

| 项 | 说明 |
| --- | --- |
| 作用 | 消费问答接口的流式事件 |
| 实现 | 原生 `fetch` + `ReadableStream` 逐块读取，按空行切帧、按 `data:` 前缀取载荷、`JSON.parse` 后按事件类型分发 |

**选型理由**：不引入 `eventsource-parser` 或类似库，是因为协议极简（每帧 `data: {json}` + 空行分隔），自己写不到 30 行，且能完全控制分块粘包的处理。引入库反而增加一层不必要的抽象。

**实现位置**：`frontend/src/api/chat.ts` 的流式函数 + `ChatView.vue` 的事件分发（`switch (ev.type)`）。

### 3.8 Vite 7.3.7

| 项 | 说明 |
| --- | --- |
| 作用 | 开发服务器、热更新、生产打包 |
| 版本 | 7.3.7 |
| 关键配置 | `server.port=5173` + `strictPort`；`/api` 代理到 `127.0.0.1:8000`；`manualChunks` 拆 `element-plus` 与 `vendor` |

**选型理由**：

- 开发期按需编译，改一个 `.vue` 文件后页面状态保留、热更新在百毫秒级——对调试流式渲染这类交互极其关键。
- 生产构建与开发同一条工具链，不需要额外维护 webpack 配置。

**`strictPort` 的实际意义**：端口被占用时**直接报错**而不是静默换到 5174/5175。开发中曾因多个 dev server 并存，导致在旧端口的页面里看新代码、误判"改动没生效"，加此配置后这类误判不再发生。

### 3.9 TypeScript 5.9.3 + vue-tsc 3.3.13

| 项 | 说明 |
| --- | --- |
| 作用 | 类型系统与类型检查 |
| 版本 | 5.9.3 / 3.3.13 |
| 检查时机 | `npm run build` 先跑 `vue-tsc --noEmit`，类型不通过则构建失败 |

**选型理由**：流式事件有 7 种类型、每种载荷不同，用联合类型（`types/index.ts` 里的 discriminated union）能在 `switch` 分支里自动收窄类型，写错字段名编译期就报错。这比运行时调试省事得多。

## 4. 后端技术

### 4.1 FastAPI 0.162.0

| 项 | 说明 |
| --- | --- |
| 作用 | HTTP 接口、依赖注入、请求校验、流式响应 |
| 版本 | 0.162.0 |

**选型理由**（针对本项目三点硬需求）：

1. **流式响应**。问答接口需要边生成边推送，框架原生支持返回可迭代的流式响应，且能设置不缓冲的响应头（`X-Accel-Buffering: no`），为后续上 Nginx 预留。
2. **依赖注入做鉴权**。`get_current_user` / `require_admin` 作为依赖挂在路由或路由组上，令牌解析、用户加载、权限判定只写一次；`/api/admin/*` 整个路由组挂 `require_admin`，新增后台接口自动受保护，不会漏。
3. **Pydantic 模型即契约**。请求体校验、字段长度约束、枚举取值（如评价只允许 `""`/`赞`/`踩`）都在模型层声明，非法请求在进入业务逻辑前就被拦截。同时 `/docs` 自动生成可交互接口文档，前后端联调不用另外维护文档。

### 4.2 Uvicorn 0.54.0 + watchfiles 1.3.0

| 项 | 说明 |
| --- | --- |
| 作用 | ASGI 服务器；开发期热重载 |
| 版本 | 0.54.0 / 1.3.0 |
| 启动参数 | `--host 127.0.0.1 --port 8000 --reload --reload-dir src` |

**选型理由**：

- 与 FastAPI 同生态，零配置即可跑流式响应。
- `watchfiles` 是热重载的关键。未安装时 uvicorn 退回 `StatReload`（轮询比对文件修改时间），且默认监听整个项目目录——包含 `.venv`（5589 个文件）与 `frontend/node_modules`。装上 `watchfiles` 后改用操作系统文件事件，配合 `--reload-dir src` 把监听范围收敛到 80 个源文件，启动与重载都明显变快。

**注意**：热重载只监听 `.py` 与 `--reload-dir` 指定的目录。**修改 `.env` 不会触发热重载**，必须手动重启。

### 4.3 Pydantic 2.14.1

| 项 | 说明 |
| --- | --- |
| 作用 | 请求/响应模型校验；工具参数模型；函数调用 Schema 生成 |
| 版本 | 2.14.1 |

**选型理由**：本项目把 Pydantic 用到了"一个模型三处复用"的程度——

```python
class PostgresqlArgs(ToolArgs):
    subject: str | None = Field(default=None, description="标的物名称或关键词")

# 同一份定义同时产出：
# ① 参数校验规则（文本长度、取值范围由 Field 约束）
# ② 给大模型看的函数调用 Schema（model_json_schema() 自动生成）
# ③ 接口文档里的参数说明
```

新增工具时不需要手写 JSON Schema，也不需要维护参数说明文档——改模型即改三处。

### 4.4 openai 3.41.0（统一客户端）

| 项 | 说明 |
| --- | --- |
| 作用 | 调用对话模型、向量模型、批量接口、文件下载 |
| 版本 | 3.41.0 |
| 封装位置 | `clients/base_client.py` + 厂商子类 |

**选型理由**：

- 智谱、DeepSeek 都提供 OpenAI 兼容端点，用同一个 SDK 只换 `base_url` 与 `api_key` 就能切换厂商，`client.chat.completions.create` 的调用方式完全一致。
- 厂商差异（如智谱 `glm-5.3` 系列必须开思考、只认 `reasoning_effort`）收敛在子类的 `_thinking_extra()` 一个方法里，上层业务代码无感知。
- 批量接口（`client.batches`）与结果下载（`client.files.content`）也在同一 SDK 内，数据加工脚本不需要另接 HTTP。

### 4.5 zai-sdk 0.2.3

| 项 | 说明 |
| --- | --- |
| 作用 | 图片解析（视觉模型） |
| 版本 | 0.2.3 |
| 使用范围 | 仅 `clients/vision_client.py` |

**选型理由**：视觉解析需要传图片文件，智谱的原生 SDK 对文件上传的处理比走通用兼容接口更直接。这是全项目唯一使用厂商专属 SDK 的地方，范围被刻意限制在图片解析，不扩散。

### 4.6 numpy 2.5.4（向量检索）

| 项 | 说明 |
| --- | --- |
| 作用 | 语义检索的相似度计算 |
| 版本 | 2.5.4 |
| 实现 | 归一化向量矩阵点积 = 余弦相似度；`argsort` 取 top-k |

**选型理由**：语料规模约 1 万条向量（512 维），一次全量点积在毫秒级。这个量级下引入向量数据库（Milvus / Qdrant / FAISS）带来的是运维负担而非性能收益。向量存成 `.npz`，进程启动时 `lru_cache` 加载一次常驻内存，检索就是一次矩阵乘法。

**升级条件**：语料涨到十万量级以上，或需要按条件过滤后再检索时，再考虑向量库——代码里 `VectorStore` 是独立类，替换不影响上层。

### 4.7 PyJWT 2.15.1 + 密码哈希

| 项 | 说明 |
| --- | --- |
| 作用 | 令牌签发与校验；密码哈希 |
| 版本 | 2.15.1 |
| 位置 | `security.py`、`api/deps.py` |

**选型理由**：接口无状态鉴权的最低成本方案——令牌自带用户 ID 与角色，服务端不存会话。过期、签名无效、用户已删除三种情况分别给出可读提示（401），而不是笼统的"认证失败"。

**注意**：令牌存于前端本地存储，属已知取舍（未用 httpOnly Cookie），因此令牌有效期需配合业务敏感度控制。

### 4.8 PyMySQL 1.2.3 + psycopg2-binary 2.9.13

| 项 | 说明 |
| --- | --- |
| 作用 | 分别连接 MySQL 与 PostgreSQL |
| 版本 | 1.2.3 / 2.9.13 |

**选型理由**：两种库并存不是随意选择，而是数据分工的结果——

| 库 | 存什么 | 为什么是它 |
| --- | --- | --- |
| MySQL | 用户、问答、会话记忆、埋点、项目记录、企业信息、违规记录 | 历史数据已在此库，业务表结构稳定 |

## 6. 模型与外部服务

### 6.1 智谱 GLM（主用）

| 项 | 说明 |
| --- | --- |
| 作用 | 对话生成、工具决策、会话摘要、向量化、图片解析 |
| 接入方式 | OpenAI 兼容端点 `/api/paas/v4` + 厂商 SDK（仅视觉） |
| 使用的模型 | 回答模型、工具轮模型、向量模型、视觉模型分别可配 |

**选型理由**：

- 国内直连、无需代理，延迟可控。
- 同一厂商同时提供对话、向量、视觉三类模型，减少供应商数量。
- 按量计费 + 资源包模式，成本可预估。

**关键适配点**：不同型号对"思考"参数的支持不一致——`glm-5.3` 系列**始终思考**、不接受关闭，常规只认 `reasoning_effort`（low/high/max）；较早型号则接受 `thinking.type=enabled/disabled`。这个差异收敛在客户端子类里按模型名前缀分流，业务代码不需要判断。前端「深度思考」开关把强度提升到 `LLM_DEEP_THINKING`（默认 `high`）：`glm-5.3` 深度模式改为显式传 `thinking.type=enabled`，因为 `reasoning_effort` 模式不返回 `reasoning_content`、前端拿不到思考过程；较早型号没有强度档位，同样映射为 `thinking.type=enabled`。常规模式仍走 `reasoning_effort` 静默推理。

### 6.2 DeepSeek（备选 + 评估）

| 项 | 说明 |
| --- | --- |
| 作用 | 备选对话厂商；**评估体系的独立评审员** |
| 接入方式 | OpenAI 兼容端点 |

**选型理由**：

- 作为对话备选，配置切换即可替换主模型。
- 作为评审员更有价值：**评估必须由与被评模型不同厂商的模型打分**，否则存在自评偏差。被评回答由智谱生成，评审由 DeepSeek 执行，这是评估结果可信的前提。
- Chat API 没有 thinking 透传参数：前端「深度思考」开启时，回答模型切换到 `DEEPSEEK_THINKING_MODEL`（默认 `deepseek-reasoner`），工具轮仍用轻量模型。

### 6.3 Tavily（联网检索）

| 项 | 说明 |
| --- | --- |
| 作用 | 本地语料外的信息补充（最新政策、公告、网页） |
| 接入方式 | REST 直连（标准库 `urllib`，无额外依赖） |

**选型理由**：它返回的是**已抽取清洗的正文段落**，不是网页 HTML——省掉了自己抓取解析的一整层。请求参数控制在"只要结果不要它自己生成答案"（`include_answer=false`），避免二次改写。

**约束**：免费额度按次数计，需留意用量；客户端超时 10 秒，超时后由工具层返回可读错误，不拖住整条问答链路。

### 7.1 数据加工脚本（自建，`batch/`）

不引入工作流框架（Airflow / Prefect），因为这是一次性加工而非周期调度。脚本设计上的两个实用点：

- **断点续跑**：并发抽取脚本只把成功行算作"已完成"，中断后重跑自动跳过，失败项自动补跑。
- **可指定输入输出**：所有脚本支持 `--input` / `--output`，避免硬编码路径导致重复跑错文件。

### 7.2 评估体系（自建，`evals/`）

不引入 RAGAS / TruLens 等评估框架，原因：本项目的评估维度很具体（工具命中、关键词、三维评分），且需要"独立厂商评审"这一条硬约束，现成框架反而要绕过它的抽象。

三类指标分工：

| 类型 | 实现 | 局限 |
| --- | --- | --- |
| 工具命中率 | 用例声明期望工具，与实际调用集求交集 | 只说明"调对了工具"，不说明"答对了" |
| 关键词通过率 | 答案与来源标题的子串匹配（已做全半角与空白归一） | 语义等价表述仍会误判，只作粗筛 |
| 三维评分 | 独立厂商模型按正确性/忠实度/完整性打分 | 有模型主观性，需配合参考要点 |

## 附：技术选型决策摘要

| 决策 | 结论 | 一句话理由 |
| --- | --- | --- |
| 是否引入 LangChain / LlamaIndex | 不引入 | 编排逻辑只有一条 ReAct 循环，自研 200 行更可控，且便于按事件流精确埋点 |
| 是否引入向量数据库 | 不引入（当前量级） | 1 万条向量用 numpy 点积已够快，加库是运维负担 |
| 是否引入工作流框架 | 不引入 | 数据加工是一次性任务，脚本 + 断点续跑足够 |
| 是否引入评估框架 | 不引入 | 需要"独立厂商评审"这一硬约束，现成框架难适配 |
| 流式通道 | 标准流式响应（单向） | 场景是单向推送，不需要双向通信 |
| 鉴权方式 | 无状态令牌 | 接口无需服务端会话，水平扩展无状态负担 |
| 模型接入 | OpenAI 兼容协议 | 换厂商只改 base_url 与 key，厂商差异收敛在客户端子类 |
| 双数据库 | MySQL + PostgreSQL | 存量业务表不动，标的物这类新维度独立建库演进 |
