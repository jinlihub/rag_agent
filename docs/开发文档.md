## 1. 项目背景与目标

### 1.1 背景

招投标行业信息密集，公开信息分散在各地交易中心、政策发布平台与第三方数据源。从业人员面临的困难集中在三点：

| 痛点 | 表现 |
| --- | --- |
| 信息分散 | 招标公告、中标结果、政策文件、企业资质分布在不同渠道，需逐站查找 |
| 检索低效 | 关键词检索无法处理"近半年安徽合肥有哪些企业中标"这类带条件与聚合的诉求 |
| 门槛较高 | 质疑时限、保证金比例、采购方式适用条件等规则性问题需专业解读 |

### 1.2 目标

| 编号 | 目标 | 在本系统中的落点 |
| --- | --- | --- |
| G1 | 招标信息智能获取 | 按项目、企业、地域、类别、时间、金额检索结构化项目记录 |
| G2 | 招标疑问智能解答 | 基于法规条文、政策全文、实务问答的知识检索与引用 |
| G3 | 实体关系可查 | 企业工商信息、违规记录、标的物与采购方/供应方的关联 |
| G4 | 数据安全与质量可控 | 登录鉴权、权限隔离、回答可溯源、人工维护闭环 |

### 1.3 本期范围

**范围内**：C 端问答（提问、流式回答、来源展示、多轮上下文、点赞点踩、历史会话）、B 端维护后台（多条件查询、标记正确、编辑回答、不需要维护）、用户注册登录、发送埋点、模型可切换、图片解析、离线数据加工与效果评估。

**范围外**：对外开放 API、移动端/小程序、个性化推荐、报表界面（仅保留埋点采集）。

## 2. 用户角色与使用场景

### 2.1 角色定义

系统存在两个维度的角色，互不替代：

| 维度 | 字段 | 取值 | 作用 |
| --- | --- | --- | --- |
| 账号类型 | `user_type` | `企业用户` / `自然人` | 描述提问者身份，注册时选定，默认 `自然人`；用于后台筛选与展示 |
| 系统权限 | `role` | `admin` / 其他 | 决定能否访问维护后台；`admin` 通过 `require_admin` 校验 |

### 2.2 权限矩阵

| 能力 | 未登录 | 普通用户 | 管理员 |
| --- | --- | --- | --- |
| 注册 / 登录 | ✓ | — | — |
| 问答、历史、点赞点踩、埋点、图片解析 | ✗ | ✓ | ✓ |
| 查看他人会话 | ✗ | ✗（仅限本人，越权返回 404） | ✗（后台按列表查看，不走会话接口） |
| 维护后台（查询全部问答、标记、编辑） | ✗ | ✗（403） | ✓ |
| 系统监控（指标与近期日志） | ✗ | ✗（403） | ✓ |

前端路由守卫与后端接口校验双重生效：`/admin/qa-list`、`/admin/system` 要求 `isAdmin`，`/api/admin/*` 要求 `role=admin`。

### 2.3 典型使用场景

| 编号 | 角色 | 场景 | 系统行为要点 |
| --- | --- | --- | --- |
| UC-01 | 销售人员 | 问"2023年10月安徽省有哪些服务类的中标项目" | 调用结构化检索工具，按时间+地域+类别筛选，分点列出项目与金额，附来源 |
| UC-02 | 采购人员 | 问"供应商提出质疑的时限是多少天" | 调用知识库检索，引用法规名称与条文要点，不逐字长抄 |
| UC-03 | 技术研发 | 问"空调的供应商和采购人有哪些" | 按标的物检索项目记录，聚合出采购方与中标方 |
| UC-04 | 任何用户 | 追问上文提到的项目细节 | 携带会话历史（近 4 组逐字 + 更早的摘要）继续作答 |
| UC-05 | 任何用户 | 打开历史会话继续聊 | 从会话列表恢复，消息按问答对展开 |
| UC-06 | 管理员 | 按"未维护"筛选，逐条审核 | 标记正确 / 编辑修正 / 标记不需要维护，修改时间同步刷新 |
| UC-07 | 管理员 | 按用户名称或问题关键词定位某条记录 | 多条件组合查询，结果为条件交集 |
| UC-08 | 任何用户 | 提问涉及最新政策，打开联网开关 | 本地检索 + 联网检索双源作答，末尾列出网页来源 |

## 4. 各模块职责与主要业务流程

### 4.1 认证模块

**职责**：账号创建与身份校验，产出访问令牌；为其它接口提供当前用户与权限判定的依赖。

**流程**：

```
注册：校验 user_type ∈ {企业用户, 自然人} → 用户名查重 → 密码哈希 → 入库 → 签发令牌并返回用户信息
登录：按用户名取用户 → 校验密码 → 签发令牌
鉴权：解析 Bearer 令牌 → 过期/无效/用户已删 分别返回 401 → 注入当前用户
授权：role != admin 时访问后台接口返回 403
```

### 4.2 问答模块（核心）

**职责**：接收问题，编排多轮工具检索与最终生成，以事件流形式逐步返回，并在结束时把问答对落库。

**主流程**：

```
① 受理与校验
   问题去空白 → 校验答案模型合法性（不在候选清单内直接 400）
   → 立即写入问答记录（此时只有问题，答案为空），得到记录 ID
   → 组装会话历史（异步触发摘要压缩，不阻塞）
   → 发出 meta 事件（携带记录 ID 与本次使用的模型）

② 意图路由（进工具循环前一次判定）
   寒暄/致谢/问身份（规则整句匹配）→ chitchat：不调工具，直接短答
   纯知识性提问（工具轮小模型三分类）→ faq：只调一次 FAQ 知识库（scope=faq），直接作答
   其余/分类失败 → complex：进入下面的完整 ReAct 循环
   FAQ 检索无可用结果时退回完整循环；chitchat / FAQ 命中后跳过联网补查

③ 检索阶段（最多 3 轮，ReAct）
   每轮：
     用轻量模型做"分析 + 决策"，输出一行分析结论与工具调用列表
     发出 analysis 事件（分析摘要）
     若工具列表为空 → 判定信息充分，结束循环
     若工具列表非空：
       逐个发出 tool_call 事件（工具名 + 参数）
       多个工具时并行执行；单工具时串行
       每个工具执行后：质量评估 → 质量不达标时发出 quality 事件 → 结果折入来源列表 → 回填为工具结果消息

③′ 主动澄清（优先于猜测）
   无历史时问题以“那家公司/那个项目/该企业”等指代开头 → 直接构造 ask_user 结果
   模型调用 ask_user → 立即发出 clarify 事件
   模型把澄清写进分析文本（未调用工具）→ 同样转成 clarify 事件
   以上均结束本轮：不执行同轮其它工具、不进入生成，等待用户补充信息

④ 联网补齐（仅复杂问题）
   用户开启联网但模型未调用联网工具时，强制补一次联网检索，保证"本地 + 联网"双源

⑤ 收束选择（按分支）
   闲聊              → 简短回应并引导到业务问题
   FAQ 命中          → 只依据本次 FAQ 结果作答，不再调工具
   无任何来源        → 要求如实说明查不到，禁止编造
   有来源但存在工具失败 → 要求只用真实检索到的内容，禁止补全来源外事实、禁止推测失败原因
   全部正常          → 常规作答

⑥ 生成阶段
   发出 sources 事件（来源面板数据）→ generating 事件
   用回答模型流式生成：深度思考开启时先发 reasoning 事件（模型返回思考过程时），
   再逐段发出 delta 事件
   生成结束发出 timing 事件（各阶段耗时与总用时）

⑦ 收尾
   发出 done 事件
   把完整答案与来源写回问答记录
```

**关键约束**：检索阶段使用的模型与生成阶段使用的模型可以不同（前者轻量、后者能力更强），由配置决定；工具集合在请求时确定，联网工具按用户开关决定是否可用。

### 4.3 会记忆与历史模块

**职责**：把历史问答转换成可续聊的上下文，并支持会话维度的浏览与删除。

**历史组装规则**：

| 历史长度 | 组装方式 |
| --- | --- |
| ≤ 4 组 | 全部逐字保留 |
| > 4 组 | 最近 4 组逐字 + 更早的按摘要表示 |

**摘要机制**：滑出窗口的问答组累积到 3 组时触发一次摘要合并，与原摘要合并后写回会话记忆；摘要生成放到后台执行，本次请求先用旧摘要与逐字内容顶上，下次提问生效。摘要必须保留实体清单（省、企业、项目、法规名）与关键数字——这是长对话最易丢失的部分。摘要失败时退化为机械拼接，不影响问答。

**流程**：

```
会话列表：按用户检索分组（按最近提问倒序），支持关键词命中问题或回答
会话恢复：取该会话全部记录，按提问顺序展开为「用户消息 / 助手消息」对，助手消息携带来源与点赞状态
删除会话：删除该会话全部问答记录与会话记忆（连带后台不可见）
清空会话：删除该用户全部记录与记忆
点赞点踩：校验归属后写入，传空值表示撤销（回落默认值）
```

### 4.4 维护模块

**职责**：为管理员提供全量问答的检索与人工修正能力，形成"机器回答 + 人工维护"闭环。

**维护状态机**：

```
【未维护】(默认)
   ├─ 标记正确 ────────▶ 【已维护】
   ├─ 编辑并保存 ──────▶ 【已维护】
   └─ 不需要维护 ──────▶ 【不需要维护】
（三种状态均可再次被编辑或改判）
```

**流程**：

```
查询：用户名称 / 问题关键词 / 账号类型 / 维护状态 / 结果评价 / 问题时间区间 组合过滤 → 分页返回
标记正确：状态置「已维护」，修改时间刷新，返回操作结果
编辑回答：校验长度 → 更新答案 → 状态置「已维护」，修改时间刷新
不需要维护：状态置「不需要维护」，修改时间刷新
记录不存在：统一返回 404
```

### 4.5 模型模块

**职责**：给前端提供可选回答模型清单、对请求侧传入的模型做合法性校验，并决定每个模型该走哪家厂商的端点。

**清单来源**：内置候选表为**扁平结构，每项带厂商标记**（智谱 / DeepSeek），一次列出全部厂商的模型；可被 `LLM_MODEL_CHOICES` 覆盖，格式 `[provider:]id:标签:说明`——3 段沿用当前厂商，4 段显式指定（跨厂商混列时用）。当前配置的默认模型永远在列。

**多厂商路由**：一个 `LLM_BASE_URL` 只能对应一家厂商，因此「模型 → 厂商」的映射由 `provider_of(model_id)` 负责：调用侧拿到模型 id 后先查厂商，再 `get_client_for(provider)` 取该厂商的客户端（每个厂商缓存一个实例，连接池不重复建）。工具轮与最终作答各自按自己的模型路由，所以支持「工具轮用智谱、作答用 DeepSeek」这类组合。

探活同样按厂商取客户端——用错 base_url 会得到 401，被误判成「模型不可用」，这是混列时最容易踩的坑。

**可用性探活**：对候选模型逐个发起极小请求，缓存 5 分钟。目的不是拦截调用，而是让前端能把“选了必然失败”的模型置灰并显示原因（余额不足、模型繁忙、模型不存在、Key 未配置）。清单接口本身不阻塞：首次返回 `available=null`，前端稍后重取。探活**串行**执行（间隔 0.6 秒）——并发打同一账户容易自己触发限流，判定反而不准。

**新增一家厂商的成本**：在 `llm_factory._BUILDERS` 登记 `provider → from_settings` 一项即可，路由、探活、前端清单都会自动跟上。

### 4.6 埋点模块

**职责**：采集"发送"按钮点击行为，口径与产品定义严格一致。

**口径锁定**：仅接受（事件名 = `"发送"按钮` 或 `发送按钮`，属性名 = `页面点击`，属性值 = `次数`）这一组组合，其余值直接拒绝入库，避免口径漂移。上报附带用户标识、会话标识与页面路径。

### 4.7 图片解析模块

**职责**：接收上传图片，交由视觉模型解析为 Markdown 文本返回，供用户贴入问题中提问。该模块只做解析，不参与问答编排。

### 4.8 工具模块（能力供给）

**职责**：把每类数据源封装为带参数声明的能力单元，供 Agent 自主选择调用。

| 工具 | 数据来源 | 适用问题 | 不适用 |
| --- | --- | --- | --- |
| `search_bidding_knowledge` | 法规 / 政策 / 实务问答索引 | 规则、时限、条件、条款依据 | 具体项目与金额 |
| `search_knowledge_graph` | 业务库中的企业信息与违规记录 | 企业工商档案、处罚记录、该企业作为采购方/代理方的项目概览、中标汇总（总次数/总金额/主要采购人 TOP3） | 完整项目清单、按标的物检索 |
| `search_postgresql` | 项目库（含标的物列） | 项目明细、按标的物检索、地域/类别/时间/金额筛选与排序 | 法规条文 |
| `graph_query` | 图数据库中的采购交易图谱 | 实体关系、多跳关联、反向追溯、共现分析 | 工商档案、违规记录 |
| `search_web` | Tavily 联网搜索 | 最新政策、本地语料外的信息 | 库内已有数据（应由本地工具回答） |
| `search_web_exa` | Exa MCP（标准 MCP server） | 同上，作为 Tavily 的备选/交叉验证引擎 | 未配置 `EXA_API_KEY` 时不注册 |
| `ask_user` | 无（不查数据） | 指代不明、实体歧义、时间口径模糊时向用户反问；可带 2-4 个快捷选项 | 信息足够时（不得代替检索） |

**统一约束**：每个工具声明三件事——参数模型、能力描述（模型据此路由）、质量判定规则。工具执行异常与参数校验失败都会被折叠为可读错误回传给模型，由模型自行换参数或换工具，不会中断对话。

### 4.9 检索模块

**职责**：为知识检索工具提供召回与排序能力。对外表现为"给定查询，返回带相关性分数的片段"，包含三件事：

| 环节 | 职责 |
| --- | --- |
| 双路召回 | 语义召回 + 关键词召回，两路共用同一份语料，按行号对齐 |
| 融合 | 按问题类型动态加权合并两路结果，同一条被两路同时召回时得分叠加 |
| 重排 | 对候选做二次排序；候选数量不足或后端不可用时保持融合序，不阻断链路 |

### 4.10 数据加工模块（离线）

**职责**：把原始表格加工为可检索、可分析的数据资产。各步骤职责：

| 步骤 | 输入 | 输出 | 职责 |
| --- | --- | --- | --- |
| 编请求 | 原始表格 | 批量请求文件 | 把每条项目名称编成一条抽取请求 |
| 抽取标的物 | 批量请求 | 抽取结果 | 逐条调用模型抽取「标的物」，支持并发与断点续跑 |
| 回填 | 抽取结果 | 含标的物列的表格 | 按记录序号对齐回填，失败项留空并统计 |
| 统计频次 | 含标的物表格 | 频次表 | 去重统计每种标的物的出现次数 |
| 导出图谱 | 含标的物表格 | 六列精简表 + CSV | 抽取「标的物/采购商/代理机构/供应商/交易额/所在地」 |
| 注入项目库 | 含标的物表格 | 项目库表 | 建表、建索引、清空后全量导入 |
| 注入图库 | 六列 CSV | 图数据 | 按行建节点与关系，实体名归一后批量写入 |

### 4.11 评估模块

**职责**：用固定用例集回放 Agent，量化回答质量与性能，为改动提供回归依据。

**两类指标**：

| 类型 | 指标 | 说明 |
| --- | --- | --- |
| 自动 | 期望工具命中率 | 用例声明期望工具，实际调用集合与之有交集即命中 |
| 自动 | 关键词通过率 | 答案与来源标题中包含用例声明的关键词（匹配前做全半角与空白归一） |
| 自动 | 各阶段与总用时、运行错误 | 直接取自事件流 |
| 评审 | 正确性 / 忠实度 / 完整性（1-5） | 由独立厂商模型打分，避免自评偏差；忠实度专门衡量"是否只使用检索来源、有无来源外编造" |

**报告产出**：明细（逐用例的轨迹、答案、评分）+ 摘要（聚合指标）+ 表格文件。

### 4.12 系统监控模块

**职责**：管理员在后台查看服务所在主机的运行状态与近期日志，不依赖任何外部监控系统。

**部署环境**：部署到 GPU 服务器后，快照反映的是**服务器主机**指标（16 vCPU / 123 GiB / NVIDIA L20 48G），而非开发机。该环境有独立显卡，GPU 一栏能取到真实数据；日志缓冲区为进程内内存，systemd 服务重启后清空，需重新积累。

**采集口径**：

| 指标 | 来源 | 说明 |
| --- | --- | --- |
| CPU | psutil | 总使用率、每核使用率、逻辑/物理核数；首次采样有 0.1 秒阻塞 |
| 内存 / Swap | psutil | 总量、已用、可用、使用率 |
| 磁盘 | psutil | 工作目录所在盘（`path`）用量 + 各已挂载分区（最多 12 个） |
| GPU | `nvidia-smi` | 利用率、显存、温度；无 NVIDIA 显卡/驱动时返回 `available=false` 与可读说明 |
| 主机 / 进程 | psutil | 主机名、系统、Python 版本、启动时间与运行时长；服务进程 PID、CPU、内存、线程数 |
| 日志 | 进程内环形缓冲 | root / rag_agent / uvicorn 日志，最多 500 条，单条截断 4000 字符 |

**日志采集**：`install_log_capture()` 在 uvicorn 完成日志配置后（`api/main.py` 导入时）挂载 `logging.Handler`；同一 `LogRecord` 沿 logger 树传播时只记录一次。监控接口自身的访问日志会被跳过，避免每 5 秒一次的轮询挤占缓冲区。缓冲区随进程重启清空。

**降级原则**：GPU 或单个分区采集失败只影响对应字段，接口整体仍返回其它指标；前端轮询失败显示错误条，不弹全局提示。

### 5.3 关键字段与取值

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `user_type` | `企业用户` / `自然人` | 注册时选择，默认自然人 |
| `role` | `admin` / 其他 | 仅 admin 可进后台 |
| `maintain_status` | `未维护` / `已维护` / `不需要维护` | 新记录默认未维护 |

### 5.4 数据一致性约定

- 提问即落库：问答记录在生成答案之前就建立，答案为空；流正常结束才写回答案与来源。中途异常时记录保留（答案为空），便于事后排查。
- 来源以 JSON 文本存放，读取时解析失败按空列表处理，不抛错。
- 摘要与问答记录通过"压缩至哪条记录"的边界推进，重复压缩是覆盖写，不会重复累加。
- 删除会话同时删除该会话的摘要，避免残留脏数据。

### 6.3 问答事件流契约

问答接口逐帧返回，每帧为一则独立事件。前端按类型分发处理，未知类型应忽略而非报错。

| 事件 | 载荷 | 触发时机 | 前端处理 |
| --- | --- | --- | --- |
| `meta` | 记录 ID、本次模型 | 流开始第一帧 | 记录 ID 供后续点赞与关联 |
| `status` | 阶段（思考/分析/质量/工具调用/生成）+ 可选工具名、参数、判定、文本 | 阶段推进时 | 显示当前进展（转圈、分析摘要、意图识别结果、"正在查 XX"） |
| `delta` | 文本增量 | 生成阶段每一段 | 追加到回答正文 |
| `reasoning` | 思考过程文本增量 | 深度思考开启且模型返回 `reasoning_content` 时 | 折叠进「深度思考」面板，不混入回答正文 |
| `sources` | 来源条目列表 | 生成开始前 | 渲染来源面板 |
| `chart` | ECharts option | 聚合工具返回分组结果时 | 回答下方渲染图表；spec 非法时静默忽略 |
| `clarify` | 澄清问题 + 候选选项数组 | 模型调用 `ask_user`（或识别出未解析指代）时 | 渲染澄清气泡；点击选项即作为下一问发送，本轮不生成回答 |
| `timing` | 各阶段耗时（键 + 秒 + 可选工具名）、总用时 | 回答完成后 | 渲染耗时行；同工具多次调用聚合并标注次数 |
| `error` | 错误信息 | 任意阶段异常 | 显示失败提示并提供重试 |
| `done` | — | 流结束 | 结束加载态 |

**耗时阶段键**：`history`（历史组装，由接口层并入）、`routing`（意图路由）、`analysis`（每轮分析）、`tool`（每次工具执行）、`generating`（最终生成）。

### 6.4 前端交互要点

| 交互 | 行为 |
| --- | --- |
| 发送后 | 用户消息立即上屏，回答区进入生成态；按钮禁用防重复提交 |
| 意图路由 | 闲聊直接短答、纯 FAQ 只查一次知识库，均不再跑完整 ReAct；耗时行显示「意图路由」 |
| 流式渲染 | 回答逐段追加，自动滚动到底部 |
| 来源与耗时 | 回答结束后展示来源面板与耗时行；历史恢复的旧消息无耗时数据 |
| 主动澄清 | 指代不明/实体歧义/时间模糊时先反问，不猜测；澄清气泡展示候选选项，点击后作为下一条用户消息发送 |
| 模型选择 | 记住上次选择；清单中不可用的模型置灰并显示原因 |
| 联网开关 | 打开后本地与联网双源作答，回答末尾需列出网页标题与完整地址 |
| 深度思考 | 记住开关状态；开启后最终作答调高思考强度（智谱 `reasoning_effort`，DeepSeek 切 reasoner 模型），工具检索轮次保持轻量；模型返回思考过程时折叠展示、正文开始即收起 |
| 历史会话 | 侧栏列表，支持关键词搜索、单条删除、清空全部 |
| 后台维护 | 筛选条件保持；行内操作后局部刷新；失败给出提示并回滚状态 |

## 7. 异常处理与约束条件

### 7.1 分层异常处理

| 层 | 策略 |
| --- | --- |
| 参数校验 | 入参越界、枚举非法、长度超限一律 400 并给出可读原因 |
| 工具执行 | 参数校验失败与运行异常折叠为可读错误回传模型，由模型换参数或换工具；不向上抛 |
| 编排层 | 任意异常转为 `error` 事件，保证事件流不硬断；已生成的内容仍会写回记录 |
| 接口层 | 业务异常转为对应状态码；不向前端泄露堆栈 |
| 前端 | 收到 `error` 事件显示失败与重试；请求层失败按网络异常处理 |

### 7.2 降级与兜底

| 场景 | 降级行为 |
| --- | --- |
| 知识索引未构建 | 检索工具返回"索引未构建，请先运行构建脚本"，其它工具不受影响 |
| 项目库不可达 | 结构化检索返回连接失败原因与排查建议，不中断对话 |
| 图数据库未配置 | 图查询工具返回"未配置"提示，其余工具正常 |
| 联网服务未配置 | 联网工具返回未配置提示；开关可开但会明确告知不可用 |
| 历史组装失败 | 本次问答按无历史处理，不影响作答 |
| 摘要生成失败 | 退化为旧摘要与逐字内容的机械拼接，不阻断问答 |
| 重排不可用或候选过少 | 保持融合后的顺序，不阻断检索链路 |
| 生成阶段异常 | 返回 `error` 事件；已产出的部分答案仍落库 |
| 工具调用但无有效结果 | 收束时要求如实说明查不到，并给出可操作建议，禁止编造 |
| 工具部分失败但有结果 | 收束时列出失败项，要求只用真实检索到的内容，禁止补全来源外事实、禁止推测失败原因 |

### 7.3 约束条件

| 类别 | 约束 |
| --- | --- |
| 输入长度 | 问题 1-2000 字；编辑回答 1-20000 字；会话标识 ≤64；历史分页每页 ≤50 |
| 工具参数 | 各工具有独立上限（如知识检索每库 1-6 条、关系查询每类 1-10 条、图查询 1-20 条），越界由参数校验拦截 |
| 检索轮次 | 单次问答最多 3 轮工具检索，超出即进入生成阶段 |
| 历史窗口 | 最近 4 组逐字保留；滑出窗口累积 3 组触发一次摘要 |
| 摘要长度 | 单次摘要不超过 800 字；历史单条回答在上下文中截断为 1500 字 |
| 来源条数 | 单次回答最多折叠 20 条来源；低于相关性阈值的条目不计入来源 |
| 数量上限 | 工具返回条数、候选重排条数均有上限，防止上下文与耗时失控 |
| 数据现实约束 | 业务库的项目表不含标的物列，标的物检索只能走项目库；图数据库未部署时图查询不可用 |
| 埋点口径 | 仅接受产品定义的单组事件三元组，其余值拒绝入库 |
| 配置生效 | 环境配置在进程启动时读取，修改后需重启服务；代码改动在开发模式下自动重载 |

### 7.4 已知限制

| 限制 | 影响 | 现状 |
| --- | --- | --- |
| 项目库未部署 | 结构化检索类问题无法作答 | 仅能如实说明查不到 |
| 图数据库未部署 | 关系与多跳类问题不可用 | 工具返回未配置提示 |
| 实体未做消歧 | 同一企业/标的物的不同写法会被当作不同实体 | 仅做首尾空白与全角归一 |
| 关键词指标脆弱 | 语义等价表述（如"2%"与"百分之二"）无法匹配 | 已做格式归一，指标仅作粗筛 |
| 会话摘要与耗时数据 | 历史恢复的消息不含耗时；摘要非逐字 | 已知取舍 |
| 来源展示 | 仅折叠前若干条，超出部分不展示 | 已知取舍 |

## 8. 附录

### 8.1 术语

| 术语 | 说明 |
| --- | --- |
| 标的物 | 招标采购的货物、服务或工程对象 |
| 会话 | 由前端生成标识、多次问答聚合而成的一组对话 |
| 维护 | 管理员对回答执行标记正确、编辑、不需要维护三类操作 |
| 工具 | Agent 可自主调用的数据能力单元，一个工具对应一类数据源 |
| 来源 | 回答所依据的数据条目，含类型、标题、时间、金额等摘要信息 |
| 收束 | 检索阶段结束后，决定以何种口径生成最终回答的环节 |
