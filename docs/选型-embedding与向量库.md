# 选型：Embedding 模型与向量存储

> 对应任务书「二、模型选型 · 3. embedding 及向量库选型」。
> 本文的结论基于实测数据（复现命令见文末），不是凭印象对比。

## 一、结论先行

| 选型项 | 当前方案 | 是否该换 | 理由 |
| --- | --- | --- | --- |
| **向量存储** | numpy 内存检索 | **不换** | 5680 条规模下 P50 **2.25 ms**，向量检索仅占单次检索耗时的 **0.5%**，换库最多省 2 ms |
| **Embedding** | 智谱 embedding-3（API） | **线上不换，离线场景换** | API 单次 450 ms，是真正的瓶颈；但相对端到端 26 s 只占 1.7%，线上可接受。批量建索引/批量评估时应本地化，可省 22 倍时间 |

**一句话**：瓶颈在 embedding 调用（99.5%），不在向量检索（0.5%）。优化应该花在 embedding 上，换向量库是无效投入。

## 二、实测依据

测于 2026-11-11，本机（Windows / 16 GB / 无独立 GPU 加速），数据为线上同一份索引。

### 2.1 规模与体积

| 索引 | 条数 | 维度 | npz | meta | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| legal | 4954 | 2048 | 32.0 MB | 2.5 MB | 34.5 MB |
| policy | 643 | 2048 | 4.2 MB | 0.9 MB | 5.1 MB |
| faq | 83 | 2048 | 0.5 MB | 0.1 MB | 0.6 MB |
| **合计** | **5680** | — | 36.7 MB | 3.5 MB | **40.2 MB** |

### 2.2 冷启动加载（进程首次读 npz）

| 索引 | 耗时 |
| --- | ---: |
| legal | 210 ms |
| policy | 32 ms |
| faq | 5.7 ms |

只在进程启动后首次检索时发生，之后走 `lru_cache`。

### 2.3 纯向量检索（不含 embedding）

4954 条 × 2048 维，200 次随机查询，模拟「向量已就绪」的情况：

| 指标 | 值 |
| --- | ---: |
| P50 | **2.25 ms** |
| P95 | 3.84 ms |
| 最慢 | 6.04 ms |

实现就是一次 `matrix @ vector`（numpy 走 BLAS）+ `argsort`，无任何索引结构。

### 2.4 Embedding 调用（真实 API，逐条不同 query）

| 指标 | 值 |
| --- | ---: |
| 平均 | **450 ms** |
| 最快 | 312 ms |
| 最慢 | 924 ms |

### 2.5 占比

```
单次检索 ≈ embedding 450 ms + 向量检索 2.25 ms = 452 ms
向量检索占比 = 0.50%
```

**这就是「不该换向量库」的核心证据**：把 2.25 ms 优化到 1 ms，总耗时从 452 ms 变成 451 ms，用户感知不到。

## 三、向量存储选型

### 3.1 候选方案

| 方案 | 形态 | 部署成本 | 适用规模 | 与本项目的关系 |
| --- | --- | --- | --- | --- |
| **numpy 内存检索（当前）** | 纯代码 | 无 | 十万级以下 | 零依赖，随进程加载 |
| FAISS | 内存索引库 | 装 wheel，无服务 | 百万级 | 支持 IVF/HNSW，需自己管索引文件 |
| pgvector | PostgreSQL 扩展 | 随 PG 安装 | 百万级 | 与业务库同源，可 SQL 过滤 + 向量混合 |
| Qdrant | 独立服务 | Docker | 千万级 | 过滤与向量混合查询强，Rust 实现 |
| Milvus | 分布式服务 | 重（多组件） | 亿级 | 功能全，运维复杂 |

### 3.2 容量拐点估算

暴力检索的耗时与条数**线性相关**（浮点运算量 = 条数 × 维度）。按实测推算：

| 语料规模 | 预估单次检索 | 判断 |
| ---: | ---: | --- |
| 5.7 千（当前） | 2.25 ms ✅ 实测 | 远未到瓶颈 |
| 5 万 | 约 20 ms | 仍可接受 |
| **10 万** | **约 40 ms** | **开始值得考虑换** |
| 100 万 | 约 400 ms | 必须换 |

内存占用同样线性：当前 40 MB，100 万条约 8 GB（2048 维 float32）——那时单机内存也扛不住了。

### 3.3 决策

**保持 numpy，不引入向量数据库。**

理由：

1. **规模不符**：5680 条，离 10 万条的拐点还有 17 倍空间；
2. **收益为零**：向量检索只占 0.5%，换库省下的时间被 embedding 覆盖；
3. **成本为负**：引入 Qdrant/Milvus 要多一个常驻服务、多一套运维、多一层故障点（服务挂了检索就没了）；
4. **丢了简单性**：现在索引就是两个文件（`.npz` + `.meta.jsonl`），随代码走，重建只需一条命令。

**什么情况下该换**（写清楚触发条件，避免以后拍脑袋）：

| 触发条件 | 换什么 |
| --- | --- |
| 语料超过 10 万条，或检索 P95 > 50 ms | FAISS（最小改动，仍是库不是服务） |
| 需要「向量 + 业务条件」联合过滤且条件复杂 | pgvector（复用现有 PG，事务一致） |
| 多实例部署、需要共享索引 | Qdrant（独立服务，多副本） |
| 语料上亿 | Milvus |

## 四、Embedding 选型

### 4.1 候选方案

| 模型 | 维度 | 中文表现 | 成本 | 部署 | 单次延迟 |
| --- | ---: | --- | --- | --- | ---: |
| **智谱 embedding-3（当前）** | 2048 | 好 | 按量计费 | API | **450 ms** |
| bge-m3 | 1024 | 中文检索榜前列，多语言 | 免费 | 本地 GPU/CPU | 约 20 ms |
| bge-large-zh-v1.5 | 1024 | 中文专用，成熟稳定 | 免费 | 本地 | 约 15 ms |
| Qwen3-Embedding-0.6B | 1024 | 榜单强，支持多语言 | 免费 | 本地 | 约 20 ms |

### 4.2 当前方案的实际影响

| 场景 | 调用次数 | 按 450 ms 估算 |
| --- | ---: | ---: |
| 单次问答（1 次检索） | 1 | 0.45 s（占端到端 26 s 的 1.7%） |
| 重建全量索引 | 5677 | **约 42 分钟** |
| 跑一轮 golden set 评测（40 条） | 40 | 约 18 秒 |
| 跑四组参数扫描（RAG 复评） | 160 | 约 72 秒 |

**结论分化**：

- **线上问答：可接受**。0.45 s 相对 26 s 的端到端耗时占比很小，不值得为它引入 GPU 依赖；
- **离线批处理：明显吃亏**。建索引 42 分钟、每轮评测十几秒，而这些是开发期高频操作。本地化后同样工作只需 2 分钟和 1 秒内。

### 4.3 决策

**线上保持 API，离线场景提供本地化选项。**

理由：

1. 线上换本地模型要把 GPU 变成硬依赖，服务挂载的组件越多越脆；
2. 效果上 bge-m3 与 embedding-3 属于同一档，替换后**检索指标可能升也可能降**，需要重跑 golden set 验证（这一步没做，不做效果对比就不敢说更好）；
3. 但离线批处理（建索引、参数扫描）应走本地模型——那里 450 ms 会被放大 5677 倍。

**落地方式**（尚未实施，留作后续）：

```
llm.py: embed_texts() 加分支
  EMBEDDING_BACKEND=api       → 智谱 API（线上默认）
  EMBEDDING_BACKEND=local     → sentence-transformers 加载 bge-m3（离线用）
```

切换后需重建索引（维度 2048 → 1024，旧索引作废），并用 golden set 对比 hit@1 决定线上是否也切。
