# 调研：低参数开源大模型与工具调用能力

> 对应任务书「二、模型选型 · 1. 调研低参数开源大模型并选出候选对象」与「2. 调研候选大模型的工具调用和深度思考能力」。
> 所有数字来自实测，复现命令见文末。

## 一、结论

| 结论 | 依据 |
| --- | --- |
| **本地部署完全可行** | Qwen3-4B 在 L20（48 GB）上跑通，显存占约 19 GB，首 token 延迟比 API 低 60% |
| **4B 不宜独立承担工具轮** | 工具命中率 70%（GLM-4.5-Air 为 95%），主要缺陷是「该查却没查」 |
| **可用于低风险场景** | 单一标的物检索、企业画像类问题全部正确 |
| **关键差距在「主动性」而非「准确性」** | 一旦决定调工具，参数命中率 80%（对比 95%），差距小于工具选择 |
| **若要用，改提示词比换模型更有效** | 4 条失败中有 4 条是压根没调工具，不是选错工具 |

**一句话**：4B 能跑、快 2.6 倍，但缺少「不确定就该查证」的意识；直接替代线上工具轮不可行，加约束后可作为降级方案。

## 二、候选模型

「同量级」按**部署成本与 API 定价档位**理解（轻量级），而非参数严格相等——线上在用的 GLM-4.5-Air 是 MoE 架构（总参数 106B / 激活 12B），单卡部署不现实，故候选只考虑 4B~9B 稠密模型。

| 模型 | 参数 | 上下文 | 工具调用支持 | 备注 |
| --- | ---: | ---: | --- | --- |
| **Qwen3-4B-Instruct-2507** | 4B | 256K | ✅ Hermes 格式 | **本次实测对象**，中英文俱佳 |
| Qwen3-8B | 8B | 128K | ✅ Hermes 格式 | 同系列上位，显存约 16 GB |
| GLM-4-9B-Chat | 9B | 128K | ✅ 需配置 parser | 与线上同厂商，便于对齐风格 |
| Llama-3.1-8B-Instruct | 8B | 128K | ✅ llama3_json | 中文能力弱于前两者 |
| InternLM3-8B-Instruct | 8B | 32K | ✅ 需配置 parser | 中文强，上下文偏短 |

**为什么先测 4B**：显存占用最小、启动最快，用来验证「本地部署 + 工具调用」这条链路是否走得通。链路通了，换 8B 只是改个模型名。

## 三、部署验证（vLLM）

### 3.1 环境

| 项 | 值 |
| --- | --- |
| GPU | NVIDIA L20，48 GB |
| 驱动 / CUDA | 580.126.09 / 12.8 |
| vLLM | 0.33.0（`uv pip install vllm`，199 个依赖） |
| 模型下载源 | hf-mirror.com |
| Python | 3.12（独立 venv，不影响项目环境） |

### 3.2 启动命令（最终可用版）

```bash
VLLM_USE_FLASHINFER_SAMPLER=0 HF_HUB_OFFLINE=1 \
nohup ~/vllm-env/bin/vllm serve Qwen/Qwen3-4B-Instruct-2507 \
  --port 8081 --max-model-len 8192 --gpu-memory-utilization 0.4 \
  --enable-auto-tool-choice --tool-call-parser hermes \
  > ~/vllm.log 2>&1 &
```

四个关键项缺一不可：

| 项 | 作用 | 不加会怎样 |
| --- | --- | --- |
| `VLLM_USE_FLASHINFER_SAMPLER=0` | 用 PyTorch 原生采样器 | 采样阶段崩溃（见 §八） |
| `HF_HUB_OFFLINE=1` | 跳过 HF 在线校验 | 遇到 429 限流，启动卡住 |
| `--enable-auto-tool-choice` | 允许模型自主选工具 | 传 `tools` 直接 400 |
| `--tool-call-parser hermes` | 解析 Qwen 的工具调用格式 | 同上 |

### 3.3 资源占用

| 指标 | 值 |
| --- | --- |
| 模型权重显存 | 7.64 GiB |
| 实际总占用（含 KV cache） | 约 19 GiB（`gpu_memory_utilization=0.4`） |
| KV cache 容量 | 72,528 tokens；8192 上下文下并发 8.85 倍 |
| 首次启动耗时 | **约 13 分钟**（其中 779 秒用于下载 8 GB 权重，无进度条） |
| 二次启动耗时 | 约 40 秒（权重与编译产物均已缓存） |

## 四、工具调用实测

### 4.1 方法

用 `evals/compare_tool_calling.py`，对 `evals/agent_set.jsonl` 的 20 条用例：

- **同一套 system prompt**（项目实际的 `build_system_prompt()`，含数据覆盖范围）
- **同一套工具 Schema**（项目实际的 4 个工具 + ask_user）
- **只换模型端点**，不执行工具，只看返回的 `tool_calls`
- 判定：期望工具是否被调用（工具命中）、期望参数是否落在实际参数里（参数命中）

这样测的是「选工具 + 拼参数」的纯决策能力，不受检索结果与生成质量干扰。

## 五、失败模式分析

Qwen3-4B 的 6 条失败，按性质分两类：

### 5.1 该查却没查（4 条，主要缺陷）

| 用例 | 问题 | 实际行为 |
| --- | --- | --- |
| ag-012 | 公开招标和邀请招标有什么区别 | 直接凭记忆作答，未查法规 |
| ag-015 | 每个月中标项目数量趋势 | 直接作答，未调统计工具 |
| ag-019 | 那家公司中标了哪些项目 | 直接作答，未反问「哪家公司」 |
| ag-020 | 帮我查一下那个项目 | 直接作答，未反问 |

**共性**：小模型倾向于「能答就答」，缺少「不确定/需查证」的自我判断。这不是工具调用能力问题，是**行为倾向**问题。

### 5.2 过度澄清（1 条，反而更严谨）

ag-006「合肥市近半年的工程类中标项目」，4B 没有直接查询，而是反问：

> 您所说的「近半年」是指最近 11 天内的项目，还是希望我按 2023 年 10 月的项目范围查询？

**它察觉到了「近半年」与数据范围（仅 12 天）的矛盾**，主动澄清。按评测口径记为失败，按用户体验可能优于直接查询。

### 5.3 两个模型共同的失败（1 条）

ag-016「2025 年政府采购新政策」：两者都查了本地政策库，未联网。**这是工具描述层面的问题**，与模型规模无关。

## 六、深度思考能力

**本次未实测**，原因：

1. Qwen3 系列的 thinking 模式需在 tokenizer 层加 `enable_thinking` 参数，vLLM 启动时需要额外配置 chat template；
2. 线上 GLM-4.5-Air 的 thinking 通过 API 参数控制，两者机制不同，难以在同一协议下公平对比；
3. 项目现有的「深度思考」是前端开关 + 模型路由，不涉及本地模型的推理链。

**待验证**：若后续要让 4B 承担推理型任务，需单独设计对比实验（同一批需要多步推理的问题，开/关 thinking 各跑一遍）。

## 七、选型建议

| 场景 | 建议 | 理由 |
| --- | --- | --- |
| **线上工具轮（当前）** | **继续用 GLM-4.5-Air** | 4B 工具命中率差 25 点，直接影响答对率 |
| 本地降级/离线演示 | Qwen3-4B 可用 | 单一标的物检索、企业画像全部正确 |
| 对延迟敏感的场景 | 4B 有明显优势（672 ms vs 3134 ms） | 但需接受准确率下降 |
| 复杂查询（多条件、统计） | 必须用大模型 | 4B 在 ag-005/015 上失败 |
| 指代澄清 | 必须用大模型或加强提示词 | 4B 在 ag-019/020 全失败 |

**如果要上 4B，优先改提示词而不是换模型**：在 system prompt 里明确「涉及具体项目/企业/金额/时效的数据，必须先调工具，不得凭记忆回答」，预期能补上一部分「该查不查」的缺口。这个改动成本远低于换成 8B 或 14B。

## 八、踩坑记录

按遇到顺序，都是实际卡住过的：

### 8.1 首次启动 13 分钟，看起来像卡死

现象：日志停在 `Initializing model took 2.35s`，之后 13 分钟无输出，`nvidia-smi` 显示 GPU 利用率 0%。

原因：**在下载 8 GB 模型权重，vLLM 下载过程不打印进度条**。

判断方法：看 `~/.cache` 目录大小是否在增长，或 `ps aux | grep -c nvcc`（编译时会有 nvcc 进程）。

### 8.2 hf-mirror 返回 429 限流

现象：`HTTP Error 429 thrown while requesting ... Rate limited. Waiting 100.0s before retry`。

原因：vLLM 启动时会向 HF API 校验模型文件是否最新，即使本地有缓存也会请求。

解决：`HF_HUB_OFFLINE=1` 跳过校验。

### 8.3 `pkill -9` 破坏 FlashInfer 缓存，之后启动必崩

现象：强杀进程后，后续每次启动都崩在 `determine_available_memory → _dummy_sampler_run → sampler`。

原因：`pkill -9` 不给进程清理机会，正在写入的 FlashInfer JIT 编译产物（`~/.cache/flashinfer`）变成半截文件，下次加载直接报错。

解决：

```bash
rm -rf ~/.cache/flashinfer
VLLM_USE_FLASHINFER_SAMPLER=0 ...   # 用 PyTorch 原生采样器
```

**教训**：停服务优先用 `pkill`（SIGTERM），让进程自己清理；只有卡死时才用 `-9`。

### 8.4 传 `tools` 报 400

现象：`"auto" tool choice requires --enable-auto-tool-choice and --tool-call-parser to be set`。

原因：vLLM **默认不启用** function calling，必须显式开启。

解决：加 `--enable-auto-tool-choice --tool-call-parser hermes`。

### 8.5 `nohup vllm` 报 command not found

现象：`nohup: failed to run command 'vllm': No such file or directory`。

原因：后台启动不继承当前 shell 的 PATH，venv 未激活时找不到命令。

解决：用绝对路径 `~/vllm-env/bin/vllm`，而不是依赖 PATH。

### 8.6 日志被覆盖，找不到上次成功记录

现象：重启后 `grep -c "startup complete" ~/vllm.log` 返回 0，但服务其实在跑。

原因：`> ~/vllm.log` 每次清空文件，新进程（可能启动失败）把旧日志冲掉了。

解决：重启时用不同日志名，如 `> ~/vllm_$(date +%H%M).log`。
