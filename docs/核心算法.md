# 核心算法

本文档系统梳理 rag-agent（招投标问答机器人）中每一个核心环节的算法原理、公式、关键参数与工程取舍，作为开发与调优的权威参考。所有算法均以当前代码实现为准，标注了对应源码位置。

> 阅读顺序建议：先看 §1 总览建立数据流全景，再按兴趣跳转。参数速查表见文末 §10。

## 1. 总览：一次问答的完整数据流

```
用户问题
   │
   ▼
┌─ 历史组装 agent/memory.py ─────────────────────────────────────┐
│ [要点摘要(system)] + [窗口外尾巴(逐字)] + [最近4组问答(逐字)]      │
└─────────────────────────────────────────────────────────────────┘
   │
   ▼
┌─ 意图路由 agent/intent.py（进循环前判定一次，工具轮小模型）────────┐
│   寒暄规则匹配 → chitchat：不调工具，直接短答                      │
│   模型三分类 → faq：只查一次 FAQ（scope=faq）→ 直接作答             │
│                complex：进入下面的完整 ReAct 循环                   │
│   路由失败/超时 → 降级 complex；FAQ 无可用结果 → 退回完整循环       │
└─────────────────────────────────────────────────────────────────┘
   │
   ▼
┌─ ReAct 循环 agent/agent.py（≤3 轮，工具轮用轻量模型 T=0.2）──────┐
│   分析：一行"已有什么 / 还缺什么"                                  │
│     │ 无 tool_calls ─────────────────────────► 进入收束           │
│     ▼ 有 tool_calls                                              │
│   工具执行：Pydantic 校验 → run() → 异常折叠 {"error": ...}       │
│     ▼                                                            │
│   质量关卡 assess_quality：ok / empty / weak / error             │
│     ├─ 不达标 → hint 回填对话，驱动下一轮换工具/换参数             │
│     │           并记入 quality_issues（收束时逐条告知模型）        │
│     ▼                                                            │
│   collect_sources：去重 / 弱分过滤 / 封顶 20 → 参考来源面板        │
└─────────────────────────────────────────────────────────────────┘
   │ 联网开启但模型没调 search_web → 强制补一次联网检索（仅复杂分支）
   ▼
收束提示按分支：_CHITCHAT_NUDGE / _FAQ_NUDGE / _LIMITED_NUDGE / _EMPTY_NUDGE / _FINAL_NUDGE（反幻觉）
   │
   ▼
最终作答（主模型流式 T=0.3；深度思考时先 reasoning 后 delta）→ 前端 Markdown 渲染
```

检索类工具内部走「混合检索」管线（§3）：

```
query ─┬─► dense 腿：embedding → 归一化向量 → 暴力点积 top(cap) ─┐
       │                                                        ├─► 加权 RRF 融合 ─► LLM 重排(≤16条) ─► top_k
       └─► sparse 腿：字符二元组 BM25 top(cap) ──────────────────┘    (k、权重按问题类型)
```

## 2. 离线索引构建（切块与向量化）

**源码**：`scripts/build_index.py`、`src/rag_agent/llm.py`

### 2.1 滑动窗口切块

```python
chunk_text(text, size=500, overlap=80)
# 短文本（≤500 字）整段一块；长文本按步长 step = size - overlap = 420 滑动切块
# [text[i : i+500] for i in range(0, len(text), 420)]
```

- **overlap=80 的作用**：条款的衔接句常落在边界附近，相邻块保留 80 字重叠，避免答案句被切缝截断后两块都检索不到完整语义。
- **500 字规模**：与 Embedding 模型的有效上下文和中文条款平均长度匹配，块太大稀释主题、太小丢失上下文。

### 2.2 三个知识库的差异化处理

| 库 | 数据源 | 向量化对象 | 元数据 | 设计动机 |
|---|---|---|---|---|
| `legal` 法条 | MySQL `legal_articles` + `legal_metadata` | 条款正文切块 | 法名/法型/条款名 + 块文本 | 法条按"条"检索，标题进元数据供 BM25 加权 |
| `policy` 政策全文 | MySQL `policy_政策全文` | `【标题】+ 块文本` 拼接后向量化 | 同左 | **块首带标题**：标题是政策最显著的语义锚，拼进向量提升召回区分度 |
| `faq` 问答对 | MySQL `faq_qa_pairs` | **只对问题文本**向量化 | 问题 + 答案 | 用户问法与 FAQ 问题同构，拿问题比对问题比"问题对答案"的相似度分布更锐利；答案只存元数据不参与向量 |

### 2.3 向量化与存储

- 调用 OpenAI 兼容 `/embeddings` 接口，**batch_size=16** 分批；
- 返回向量做 **L2 归一化**（零向量范数兜底为 1，防除零）：归一化后**点积即余弦相似度**，检索阶段不需要再算范数；
- `float32` 存储进 `data/index/{name}.npz`（向量矩阵）+ `{name}.meta.jsonl`（逐行元数据，**行号 i 严格对齐**——这个行号 `row` 是后面 dense/sparse 两路去重融合的对齐键）。

### 2.4 FAQ 增量重建（B 端确认触发）

全量 `build_index.py` 要重算法条/政策（几分钟），而运维每天只确认少量问答，所以 FAQ 单独一条轻量路径：

- **触发**：管理员编辑保存 / 标记正确 / 按簇确认后，`faq_expansion.py` 先粗筛（问题 ≥6 字、非寒暄、含疑问特征；回答 ≥20 字且非「本次未能检索到…」兜底话术），合格则写入 `faq_qa_pairs`（同问题覆盖更新，天然幂等）。
- **重建**：后台线程调用 `retrieval/faq_index.py`，从 `faq_qa_pairs` 全量读问题（80 条量级，「全量重算 faq」本身就是秒级增量），重新 embed → 写临时 npz/meta → `os.replace` 原子替换，避免并发检索读到半截索引。
- **生效**：重建后清掉 `get_store` / `get_sparse` 的 `lru_cache`，下一次检索重新加载新语料；dense 与 sparse 共用 meta 行号，必须一起更新。
- **幂等/容错**：同问题只保留一条；重建失败只记日志，FAQ 行已写入，下次确认再次触发；管理端请求不等待向量化。

## 3. 混合检索：dense + sparse → 加权 RRF 融合 → LLM 重排

**源码**：`src/rag_agent/retrieval/{vector_store,sparse,fusion,rerank}.py`、`src/rag_agent/tools/rag_tools.py`

### 3.1 dense 腿：NumPy 暴力余弦

```python
q = embed(query)                       # 同样 L2 归一化
scores = vectors @ q                   # (N,d)·(d,) → 点积即余弦
top = np.argsort(-scores)[:top_k]
```

- **为什么不引 FAISS/Milvus**：一期语料约 1 万条（法条 ~5k + 政策切块 + 问答对 82），`O(N·d)` 暴力点积在 NumPy 里是毫秒级，引入向量库徒增运维成本；语料涨两个量级再升级（`vector_store.py` 模块注释的既定决策）。
- 每条结果携带 `row`（语料行号）与 `score`（余弦，0~1）。

### 3.2 sparse 腿：字符级 BM25（中文无分词器的替代方案）

**源码**：`src/rag_agent/retrieval/sparse.py`

**切词**：中文无轻量分词器可用，取**字符二元组（bigram）**近似词粒度——"质疑时限" → `质疑 / 疑时 / 时限`；ASCII 连续串按整词（如 `EPC`、`ISO9001`）；单个汉字串退回单字。

**BM25 打分**（k1=1.5，b=0.75，经典取值）：

```
score(q, d) = Σ_t∈q  IDF(t) · tf(t,d) · (k1 + 1) / (tf(t,d) + k1 · (1 - b + b · |d|/avgdl))
IDF(t)      = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
```

**字段加权重复**：构建时按库配置把某些字段内容重复拼接（等效于提高 tf 与命中概率），让标题类字段的命中强于正文长尾：

| 库 | 参与字段（×重复次数） |
|---|---|
| legal | 法名 ×2 · 条款名 ×2 · 正文 ×1 |
| policy | 标题 ×2 · 正文 ×1 |
| faq | 问题 ×2 · 答案 ×1 |

**dense+sparse 双腿的价值**：法规名/条款号/专有名词这类强特征词 Embedding 常不到位，BM25 精确命中补得上；反之概念类问题问法与原文措辞差异大，语义近似靠 dense。两路共用同一份语料（同一 `meta.jsonl`），靠行号 `row` 对齐。

### 3.3 问题类型分类（规则版意图识别）

**源码**：`src/rag_agent/retrieval/fusion.py`

用**正则关键词**而非模型分类，因为检索工具轮每轮都发生，规则毫秒级、可解释，判错的代价只是融合权重略偏：

- `_LEGAL_RE`（法规/程序类）：命中"法/条例/办法/条款/第N条/依据/时限/期限/日内/个工作日/质疑/异议/投诉/保证金/评标/开标/废标/流标…"即判 `legal`。注意 `(?<![方做想说不算])法` 用负向后顾排除"方法/做法/想法/说法"等误报；
- `_CONCEPT_RE`（概念解释类）："什么是/含义/定义/为什么/区别/对比…"；
- 两者都不中 → `general`。**legal 优先判定**（命中即强信号）。

### 3.4 加权 RRF 融合

**公式**：`RRF(doc) = Σ_i  w_i / (k + rank_i)`，`rank_i` 是该文档在第 i 路召回里的排名（从 1 起）。

- 两路结果按行号 `row` **去重合并**：同一块被两路同时召回时分数叠加——这正是 RRF 的核心价值（双路一致命中 = 强信号）；
- 融合分除以最大值**归一到 0~1**，供前端"相关性 %"展示，并保证重排失败回退融合序时分数仍可读。

**参数随问题类型变化**（`_PROFILES`）：

| 问题类型 | k | dense 权重 | sparse 权重 | 直觉 |
|---|---|---|---|---|
| legal | 30 | 0.4 | **0.6** | 法名/条款号/术语是强特征词，BM25 精确命中远比语义近似可靠；关键词命中通常就在头部，**k 取小放大头部差距** |
| conceptual | 80 | **0.7** | 0.3 | 问法与原文措辞差异大，语义相关块往往排得深；**k 取大抹平头部效应**，让深排的语义命中能上来 |
| general | 60 | 0.55 | 0.45 | 文献默认 k=60，近似均衡略偏 dense |

> k 的语义：k 越小，`1/(k+rank)` 随排名衰减越陡，头部排名的票越值钱；k 越大越接近"只要进前几名贡献都差不多"。

### 3.5 LLM 重排（Rerank）

**源码**：`src/rag_agent/retrieval/rerank.py`

**流程**：融合结果过量召回（`cap = min(top_k×3, CANDIDATE_CAP=16)`）→ 候选截断每条 260 字（打分只需主旨）→ **listwise 一次调用**让小模型给全部候选打 0~10 分 → 归一 0~1 → 稳定排序取 top_k。

- **listwise 而非 pointwise**：一次调用给全部候选打分，比逐条调用省 N-1 次请求；实测 glm-4.5-air 打分一次约 1.8s。
- **打分提示词锚点**：`10=直接包含答案 / 7=高度相关 / 4=部分相关 / 0=完全无关`，输出 JSON `{"scores":[{"i":编号,"s":分数}]}`，缺编号/越界/非法 JSON 一律按 -1 沉底（宁缺毋滥）。
- **为什么不用智谱官方 /rerank 接口**：实测在本语料上判别度不足（候选分数全部 ≈1.0，连无关对照都有 0.92），故自建 LLM listwise；另保留 `RERANK_BACKEND=api` 接 Jina/Cohere/SiliconFlow 风格专用 rerank 模型（如 bge-reranker）。
- **降级链**：关闭（`off`）/ 候选不足 2 条 / 调用失败 → 返回 None，调用方**保持融合序截前 top_k**，绝不阻断检索链路。同分按原索引稳定排序，不打乱向量召回的相对次序。

### 3.6 弱结果阈值 WEAK_SCORE = 0.35

全链路统一的相关性下限，两处生效：

1. **质量关卡**（§4.2）：最高分 < 0.35 → 判 `weak`，回填"相关性偏低"的换策略建议；
2. **参考来源**（`collect_sources`）：低于阈值的条目视为检索噪声，不进前端"参考来源"面板。

## 4. ReAct Agent 循环

**源码**：`src/rag_agent/agent/agent.py`、`agent/intent.py`、`agent/prompt.py`、`tools/base.py`

### 4.0 意图路由前置（简单问题不跑完整 ReAct）

**源码**：`agent/intent.py`。进工具循环前先判定一次，三档分流：

| 意图 | 判定方式 | 后续动作 |
|---|---|---|
| `chitchat` | 正则整句匹配寒暄/致谢/告别/问身份（零模型调用） | 不调工具，追加 `_CHITCHAT_NUDGE` 直接短答 |
| `faq` | 工具轮小模型单标签分类（`max_tokens=64`，T=0） | 只调一次 `search_bidding_knowledge(scope="faq")`，回填标准 tool 消息后直接作答（`_FAQ_NUDGE`） |
| `complex` | 其余（含分类失败降级） | 走 §4.1 完整循环 |

工程取舍：

- **规则优先**：寒暄用正则 `fullmatch`，毫秒级且零成本；句子一旦带业务内容（"你好，查一下…"）就不整体匹配，交给模型分类，避免误判；
- **宁可多查一轮**：模型分类不确定、调用超时/报错一律降级 `complex`——路由是性能优化，不能成为故障点；
- **FAQ 失败可回退**：FAQ 检索 `assess_quality` 不是 `ok`（空/弱/报错）时记录 `status:quality` 并**退回完整循环**，避免把法律/政策类问题判死；
- **跳过联网补查**：`chitchat` / FAQ 命中后 `skip_tools=True`，ReAct 轮次置 0、强制联网补查也跳过；FAQ 分支只保证"一次检索"，不叠加第二数据源；
- **可观测**：路由耗时记为 `timing.routing`，前端显示为「意图路由」；路由结论以 `status:analysis` 文本回显（"意图识别：…"）。

### 4.1 循环结构（Reason → Act → Observe）

`MAX_TOOL_ROUNDS = 3`，每轮：

1. **Reason**：轻量模型（`llm_tool_model`，T=0.2）读对话产出"分析：已获得什么/还缺什么"，前端以 `status:analysis` 事件展示前 200 字；模型判定信息充分时不再产出 `tool_calls`，循环收束；
2. **Act**：模型输出一个或多个 tool_calls；
3. **Observe**：逐个执行工具，结果 JSON 序列化后以 `role:"tool"` 消息回填对话。

**双模型分工**是省时省钱的关键：选工具/拼参数不需要旗舰模型，工具轮全部用轻量模型；只有最终作答用主模型（T=0.3，流式）。

### 4.2 结果质量关卡（assess_quality）

**源码**：`tools/base.py`。每个工具执行后立即检查结果质量，四态判定：

| verdict | 触发条件 | 动作 |
|---|---|---|
| `error` | 结果含 `{"error": ...}`（参数校验失败/执行异常/连接失败） | hint 随结果回填，建议换其他工具或方式重试 |
| `empty` | 来源条目数为空 | hint 用该工具定制的 `empty_hint`（换关键词/换 scope/改用其他工具） |
| `weak` | 有结果但最高相关性分 < 0.35 | hint 指明"相关性偏低（最高 X.XX）" |
| `ok` | 通过 | 无额外动作 |

- 非 ok 时：`status:quality` 事件通知前端，**质量结论（verdict + hint）合并进回填给模型的结果**，驱动下一轮换工具/换参数——模型"知道"上一把没查好，而不是拿着空结果继续编；
- 同时把问题记入 `quality_issues` 列表，收束时逐条告知模型（见 §5.2）；
- **图谱工具的定制**：`search_knowledge_graph` 逐关系查询、单关系失败不判负（结果里 `edges` 与 `errors` 分开），只有全部关系都失败才判 `error`——避免一张表缺失拖垮整体判定。

### 4.3 工具层的两层容错（BaseTool.execute）

- **参数校验失败**（Pydantic `ValidationError`）：错误压成一行可读文本，折叠为 `{"error": "参数校验失败: ..."}` 回给模型 → 模型读得懂、能自我纠正参数；
- **执行异常**：折叠为 `{"error": "工具执行失败: 类型: 消息"}`，对模型隐藏内部堆栈细节，对话流绝不因单个工具崩溃而断掉。

工具 Schema（OpenAI function calling 格式）由 Pydantic 参数模型 `model_json_schema()` **自动生成**，增改工具参数无需手写维护 tools 列表。

### 4.4 联网补查与工具视图裁剪

- 联网开关关闭时，`search_web` / `search_web_exa` 直接从工具视图剔除；模型若仍尝试调用，返回明确错误"联网搜索未开启（用户未打开联网开关）"，避免其反复尝试或凭记忆硬答；
- 联网开启时系统提示词要求"本地 + 联网"双源必答；若 3 轮跑完模型**始终没调**任何一个联网工具，Agent **伪造一次 tool_calls（id=`forced_<工具名>`）强制补查**——优先 Tavily，未配置 `TAVILY_API_KEY` 时退回 Exa——把联网结果回填后才收束，保证双源承诺不落空。

### 4.5 前端「深度思考」开关

开关只作用于**最终作答**，工具轮（选工具/拼参数）保持轻量模型，避免每轮检索都多等一次思考：

- **智谱 GLM**：沿用所选回答模型，把 `thinking` 从 `LLM_FINAL_THINKING`（默认 `low`/`disabled`）提升为 `LLM_DEEP_THINKING`（默认 `high`）。`ZaiClient` 按模型名分流：`glm-5.3` 系常规走 `reasoning_effort`，但**深度模式改为显式传 `thinking.type=enabled`**——实测 `reasoning_effort` 模式不返回 `reasoning_content`，且两者同传时思考内容仍被隐藏；较早型号无强度档位，`high/max` 同样映射为 `thinking.type=enabled`。
- **DeepSeek**：Chat API 没有 thinking 透传参数，开启后回答模型切换到 `DEEPSEEK_THINKING_MODEL`（默认 `deepseek-reasoner`），API 的 `meta` 事件报告实际使用的模型。
- **思考过程展示**：最终作答流式调用中，若 `delta.reasoning_content` 非空，Agent 发送 `reasoning` 事件；前端折叠成「深度思考」面板，正文第一个 token 到达时自动收起。深度模式对智谱/DeepSeek 均会请求可返回的思考过程；常规模式保持静默推理。

## 5. 反幻觉机制（三层防线）

pg-003 类翻车（编造"数据库异常"+ 来源外金额）催生的系统化防线。

### 5.1 第一层：系统提示词的事前约束（agent/prompt.py）

- "涉及具体项目、企业、金额、条款的问题**必须先调用工具**查真实数据，禁止凭记忆编造"；
- "检索结果为空、报错或与问题条件不匹配时，只能如实说明'未检索到符合条件的记录'；**严禁推测失败原因**（'数据库异常''系统故障''主库无法访问'），**严禁补充检索结果之外的项目名、企业名、金额、日期——即使你确信真有其事也不得写入**"；
- **数据覆盖注入**：启动时查 `bid_subjects` 的 `MIN(publish_time) ~ MAX(award_time)` 注入提示词，让模型第一次就把"最近半年"这类相对时间**换算到有数据的时段**去查，而不是拿今天往回推（推到覆盖期外只会空查）；库不可达时静默降级为"未知"。

### 5.2 第二层：收束提示的事中拦截（agent/agent.py）

3 轮跑完后，按本轮检索质量三选一注入收束指令：

| 收束指令 | 触发条件 | 核心纪律 |
|---|---|---|
| `_EMPTY_NUDGE` | 调过工具但全程无任何可用来源 | 如实告知"基于现有数据暂时无法回答" + 给调整建议；**禁止编造任何数据、禁止推测失败原因** |
| `_LIMITED_NUDGE` | 有来源但存在失败/不达标的数据源（quality_issues 非空） | 四条铁律：① 只能用工具实际返回的内容，来源外的项目名/企业名/金额/日期**即使确信真有其事也不得写入**；② 数据源不可用时不推测原因，只说"本次未能检索到符合条件的数据"；③ 结果与问题的时间/地域/类别不匹配时如实指出，不得硬凑；④ 给 1-2 条调整建议 |
| `_FINAL_NUDGE` | 检索顺利 | 直接作答；不足时如实说明局限；禁止编造数据、禁止引用不存在的来源 |

`quality_issues` 的累积在循环内完成（每次 quality 判定非 ok 就追加 `工具名（verdict：hint）`），收束时拼接进 `_LIMITED_NUDGE` 的 `{issues}` 占位符——模型能精确知道"哪把查询出了什么问题"，而不是笼统被告知"有些失败"。

### 5.3 第三层：来源面板的事后可核查（tools/base.py）

回答正文之外，`collect_sources` 把工具结果折叠成引用列表：每工具取前 5 条、`(kind, title)` 去重、弱分（<0.35）过滤、全局封顶 20 条。前端"参考来源"面板让用户能逐条核对答案主张的出处——编造内容在面板里找不到对应来源，立即暴露。

## 6. 结构化与图数据检索（三个确定性数据源）

与 §3 的"语义检索"相对，这三类工具走**确定性查询**：参数化 SQL / 预定义 Cypher 模板，模型只填参数。

### 6.1 PostgreSQL 标的物检索与时间夹取算法

**源码**：`tools/rag_tools.py`（`SearchPostgresqlTool`）、`retrieval/sql_search.py`（`clamp_date_range`）

**动态 WHERE 组装**：keyword（title/project_name/purchaser/winner 四字段 LIKE，通配符转义）/ province / city / category / only_awarded / 时间范围，全部占位符传参防注入。关键细节：

- **时间列随语义切换**：`only_awarded=True` 按 `award_time`（中标时间）过滤排序，否则按 `publish_time`——用户问"10 月的中标项目"和"10 月发布的招标"过滤的是不同的列；
- 排序 `time`（时间倒序）/ `amount`（中标金额倒序）；`LIMIT` 夹在 1~10；
- 金额统一换算 `award_amount_wan = round(金额元 / 10000, 2)`——模型直接拿万元表述，避免它自己换算出错。

**时间夹取（clamp_date_range）——杜绝"拿错范围空查"的核心算法**：

```
输入：请求范围 [date_from, date_to]，表的实际覆盖 [lo, hi]（SELECT MIN/MAX 实时求）
1. 无时间条件 → 原样返回
2. 有交集（req_from ≤ hi 且 req_to ≥ lo）→ 原样返回（交集外本就查不到东西，交给 WHERE）
3. 完全无交集 → 按请求的等长时段贴齐最近的覆盖边界：
     span = 请求区间天数（缺一侧时用兜底 180 天）
     请求比数据更新（req_from > hi）：改查 [hi - span, hi]
     请求早于数据（req_to < lo）  ：改查 [lo, lo + span]
     并返回 note 说明"请求时间超出数据覆盖（lo~hi，原因），已自动改查 new_from ~ new_to"
```

note 随工具结果回传模型 → 回答时向用户解释实际查询的时间范围，而不是沉默地返回一堆不在所问时段的数据。

### 6.2 MySQL 知识图谱（search_knowledge_graph）

**源码**：`tools/rag_tools.py`。围绕实体查 5 类关系（各一条参数化 SQL 模板）：工商信息（`enterprise_企业信息`）、中标的项目 / 作为采购人的项目 / 作为代理机构的项目（`bid_subjects` 三个方向）、违法违规记录（`enterprise_违法违规记录`）。

- **逐关系容错**：每类关系独立 try/except，失败进 `errors` 字典不影响其他关系（一张表缺失不拖垮整体）；
- 实体名走 LIKE 模糊匹配（全称/简称都能命中）；
- **中标汇总**（wins 分支附加 `wins_summary`）：明细只有前 `limit` 条，算不出总量，因此另跑两条不带 LIMIT 的聚合 SQL——全量中标次数、总金额（元→万元），以及按中标次数排序的主要采购人 TOP3（含各自次数与金额）；汇总失败只写进 `errors.wins_summary`，不影响明细；
- **企业画像模板**：`agent/prompt.py` 用「企业主体词 + 实力/背景/靠谱等评价词」识别画像类问题（排除"哪些/如何判断/资质要求"等列表与规则问法），提示词规则 6 与收束指令模板要求按「概况 / 经营状况 / 中标表现 / 风险提示」四节作答；每节只写工具返回的内容，缺数据时逐节说明，禁止主观评级。

### 6.3 Neo4j 采购交易图谱（graph_query）

**源码**：`tools/graph_tools.py`、`retrieval/neo4j_client.py`。

**图模型**：节点 `Item(标的物)` `Purchaser(采购商)` `Supplier(供应商)` `Agency(代理机构)` `Location(所在地)`；关系 `(Purchaser)-[:采购{amount}]->(Item)`、`(Supplier)-[:中标{amount}]->(Item)`、`(Purchaser)-[:委托]->(Agency)`、`(Item)-[:位于]->(Location)`。

**安全设计**：模型**不能写 Cypher**，只能从 4 个只读模板中选一种并填参数（实体名 + limit），杜绝语法错误与危险查询：

| kind | 语义 | Cypher 骨架 |
|---|---|---|
| `entity` 实体画像 | 某实体的出边/入边各 limit 条 | `MATCH (n{name})` + 双 `OPTIONAL MATCH` + `collect(DISTINCT …)[..limit]` |
| `reverse` 反向关联 | 标的物被谁采购/被谁中标 | `(Purchaser)-[:采购]->(Item{name})` 与 `(Supplier)-[:中标]->(Item{name})` 双入口 |
| `path` 多跳穿透 | 采购商 p 经供应商 s 穿透到 s 服务过的其他采购商 | `(p)-[:采购]->(i)<-[:中标]-(s)-[:中标]->(i2)<-[:采购]-(p2)` 且 `p2.name ≠ p`，按 `count(DISTINCT i2)` 降序——**共享供应商数量即关联强度** |
| `cooccur` 共现分析 | 与某供应商中标过同一标的物的其他供应商 | `(s)-[:中标]->(i)<-[:中标]-(s2)` 且 `s2 ≠ s`，按共享标的物数降序，每条采样 3 个共同标的物 |

多跳/反向/共现正是关系型库做起来别扭、图数据库一行 Cypher 的事——这是引入 Neo4j 的根本理由。

## 7. 联网搜索（Tavily + Exa MCP）

**源码**：`src/rag_agent/web_search.py`（Tavily）、`src/rag_agent/tools/mcp_tools.py`（Exa）。

两个搜索引擎，模型按需择一或交叉验证：

| 引擎 | 接入方式 | 工具名 | 特点 |
|---|---|---|---|
| Tavily | REST 直连（urllib，零额外依赖）`POST https://api.tavily.com/search` | `search_web` | 返回已抽取清洗的正文摘要 + 0~1 相关性分 |
| Exa | **标准 MCP server**（官方托管 Streamable HTTP `https://mcp.exa.ai/mcp`） | `search_web_exa` | 另一家搜索索引，补充 Tavily 覆盖不到的结果 |

- Tavily 响应清洗：title 空回退用 url；content 截 400 字；score 保留 3 位（原生 0~1，与 WEAK_SCORE=0.35 直接兼容）；
- Exa 调用链：`asyncio.run`（已在事件循环则切独立线程）→ MCP `initialize` → `call_tool("web_search_exa")`；结果优先取 `structured_content`，否则按 `Title:/URL:/Text:` 分块解析，归一化成 `{"matches": [{title,url,content}]}`；
- 两者都归 `source_kind="web"`，前端「参考来源」统一显示为「网页」；
- 联网开关（前端 web-chip，localStorage 持久化）→ 工具视图增删 + 系统提示词双源规范 + 强制补查（§4.4）三层联动；强制补查优先 Tavily，未配置时退回 Exa；
- 未配置 `TAVILY_API_KEY` / `EXA_API_KEY` 时：Tavily 工具报 `NotConfigured`；Exa 工具在配置缺失时**不注册**（不占工具列表），避免模型选到必然报错的工具。

## 8. 会话记忆：历史滚动压缩

**源码**：`src/rag_agent/agent/memory.py`

**组装结构**（按时间序拼进 messages）：

```
[要点摘要(system)] + [滑出窗口但未压缩的组(逐字)] + [最近 4 组(逐字)]
```

**滚动压缩算法**：

```
HISTORY_WINDOW = 4    最近 4 组问答逐字保留（上下文新鲜区）
COMPRESS_MIN_BATCH = 3 滑出窗口的组攒够 3 组才压一次摘要（控制摘要 LLM 调用频率，约每 3 个新问题触发）
ANSWER_CLIP = 1500    逐字保留时单条历史回答的截断
SUMMARY_CLIP = 800    摘要长度上限

流程：rows > 4 组时，窗口外的"尾巴"（stale）攒够 3 组 → 旧摘要 + stale 合并再压一次 →
     新摘要持久化到 session_memory 表（用 upto_qa_id 标记覆盖边界，增量推进、重复压缩覆盖）
```

**可靠性设计**：

- 摘要生成失败**绝不阻断问答**：退化为旧摘要 + 逐字的机械拼接（各截一半长度）；
- 压缩提示词按本项目真实翻车案例设计（"您共查询了 5 个省"漏掉最早一个）：**实体清单（查过哪些省/企业/项目）必须逐条保留**、每问核心结论与关键数字、用户纠正与偏好、未回答的追问意图——实体清单正是长对话摘要里最容易被截断丢掉的部分。
